学习方法特点
1. 属于“目标—路径—反馈依赖型”。学习效率最高的情况是：目标非常具体 → 路径提前拆好 → 每一步足够小 → 做完能看到结果 → 有明确验收标准 → 下一步自然出现。比如：“学习异步任务”太大，无从下手，但，“用BackgroundTasks写一个sleep 1s任务→curl验证立即返回→解释TestClient为什么表现不同”，很好。因为它同时具备：明确动作、短反馈、真实结果、知识锚点。
2. “工程驱动学习”优于“教材驱动学习”。不应该先“把FastAPI学完→数据库学完→Redis学完→RAG学完→开始项目。”，而应该“我要实现一个功能→碰到FastAPI BackgroundTasks→先实现→再理解机制→合上代码重写→接受测试。”知识围绕问题长出来，更容易记。
3. 需要“渐进式难度”，不适合突然从AI辅助切到完全闭卷。因为完全不会的时候，让你坐在那里“独立思考30分钟”，很容易变成痛苦、走神，最后看答案。但一直让AI告诉你，也会形成一种很危险的幻觉“看懂 = 会。”所以最适合的是逐渐撤掉辅助。

一个以后贯穿你所有学习的“五级辅助系统”。
- L0：AI直接告诉你答案，你照着实现。适合完全陌生知识第一次接触。
- L1：AI不给代码，只给步骤/伪代码/关键API，你自己实现。
- L2：AI只给需求、验收标准和错误现象，不告诉实现方法。
- L3：完全闭卷，从需求独立实现。
- L4：不仅实现，还能面对随机变化和追问：改需求、找bug、解释trade-off。

Java、Agent、论文、六级全部走同一个循环（后三个重要）：输入 → 模仿 → 回忆 → 变式 → 输出 → 间隔复测。

不要再用：“BackgroundTasks和Celery有什么区别？思考一下。”，因为很多不懂所以懒得想，改成“强制选择 + 举证”。比如：“用户上传一份500MB PDF，解析平均20分钟。当前服务有3个FastAPI实例，要求实例重启后任务不能丢。BackgroundTasks还是Celery？只能二选一，先选，再说两个理由。”这时候你必须做判断。然后再追：“现在需求变成：头像上传以后异步生成缩略图，平均80ms，失败了用户重新上传也没关系。还上Celery吗？”，开始感受到边界。最后才问：“所以BackgroundTasks和Celery的分界线是什么？”，这比背定义强很多。
AI不能主要扮演“答案生成器”。应该扮演四个人：面试官、出题人、故障制造者、验收员。











《个人学习与行动协议 V1.4》

一、这套协议解决的核心问题

我的主要问题不是“不能坚持”。过去的健身已经证明，只要目标明确、路径清晰、反馈稳定，我能够长期执行，中断以后也能够回来。

目前真正需要解决的是：

1. 容易把“准备”误认为“推进”。
2. 容易选择低风险、低反馈的代理任务，长期不接触最终目标。
3. AI辅助产生大量“我看懂了”的错觉，但没有转化成独立能力。
4. 从“AI提供信息”切换到“自己验证”时，容易休息、刷手机或换任务。
5. 面对有明确输赢、会暴露真实能力的任务，更容易延长准备期。
6. 容易用“做其他有意义的事情”逃避当前最重要、最困难的任务。
7. 单次执行失败以后，容易从行为评价升级成人格评价，再通过发狠制定高压计划。
8. 喜欢持续寻找“真正的问题”“最关键的方法”，存在用优化学习方法代替实际训练的风险。

所以现在的核心任务是建立：“定义真实终点 → 尽早接受现实检验 → 暴露瓶颈 → 针对训练 → 再次接受检验”的稳定循环。


二、最高原则：目标稳定，方法可变

不因为一天状态不好、一次任务失败、一个新观点，就重新设计整个学习体系。运行流程固定为：

定目标
→ 设计当前方法
→ 执行
→ 收集结果和感受
→ 判断与目标的差距
→ 定位问题
→ 最小幅度修改方法
→ 再执行。

修改方法必须建立在真实执行暴露的问题上，禁止：“理论上这个新方法似乎更好，所以重新换一套。”如果旧方法没有出现可观察的失败，就不优化。


三、第一原则：从真实终点反推，而不是从“我觉得应该学什么”正推

任何重要目标开始前先回答：

“现实世界究竟通过什么结果判定我成功？”

例如：

找实习：
不是“学好Agent”。
而是“投递→简历通过→笔试/面试通过→获得offer”。

英语：
不是“每天背单词、磨耳朵”。
而是“面对真实英语材料能理解；面对真人能够表达和交流；六级则直接对应考试得分”。

论文：
不是“读很多论文”。
而是“形成明确研究问题、benchmark protocol、实验结果、论文内容并通过开题/答辩”。

扣篮：
不是“身体更强”。
而是“标准篮筐真实完成扣篮”。

永远区分：

目标 ≠ 指标 ≠ 方法。


四、先碰A，再决定练什么B

过去常见模式：

我想完成A
→ 我认为先学会B才能做A
→ 长时间训练B
→ 从来没有验证B是否真的是A当前的瓶颈
→ B给我大量努力感
→ A几乎没推进。

以后改成：

A
→ 尽可能直接测试A
→ A在哪里失败？
→ 找到当前瓶颈B
→ 针对性训练B
→ 回到A重新测试。

核心口诀：

“先碰终点，再补能力；不要等能力齐了，才第一次碰终点。”

例如找实习：

错误：
看Agent视频→学FastAPI→学RAG→学MCP→做项目→以后再改简历→以后再投。

正确：
看真实JD→检查当前简历→写目标简历bullet→发现缺项目证据→反推项目功能→开发→写进简历→投递→根据实际反馈重新训练。


五、所有“B→A”都必须有因果假设

开始一个长期训练之前问：

1. 如果B做得很好，A真的会明显提高吗？
2. A失败的人，通常真的是B不够好吗？
3. 有没有离A更近、更直接的动作？
4. 能不能尽快测试B→A到底有没有效果？

例如：

100个俯卧撑不是扣篮。
背100个单词不是英语交流。
看10小时Agent视频不是Agent开发能力。
刷100道算法题也不自动等于面试算法能力。

这些最多都是代理指标。代理指标可以使用，但不能冒充最终目标。


六、目标距离原则

一个动作离最终现实评分越近，反馈价值通常越高。

以找实习为例：

看经验帖——很远。
看技术教程——远。
跟着写项目——较远。
独立实现项目——较近。
项目写进简历——更近。
Mock Interview——很近。
真实投递——很近。
真实面试——直接评分。

不能永远生活在离目标4—6层的安全区域。每个阶段都必须周期性出现“近目标行为”，用真实反馈校准训练方向。


七、问题驱动，而不是教材驱动

默认禁止这种学习路径：“先系统学完FastAPI→数据库→Redis→RAG→Agent，然后做项目。”

优先：

“我要实现功能X
→ 开始做
→ 撞到问题Y
→ 学解决Y需要的最小知识
→ 解决
→ 回项目。”

例如：不是“今天学习异步任务。”，而是“用BackgroundTasks执行sleep 1s→curl验证接口立即返回→观察TestClient行为差异→用于文档异步解析。”知识围绕现实问题生长。


八、知识不要求全部理解到底层

知识分三级：

核心掌握：
与求职、项目核心设计、论文贡献等直接相关，要求独立使用、解释、迁移。

会用即可：
知道用途、输入输出、基本边界，能够正确调用，需要时再深入。

暂时黑盒：
目前不阻塞最终目标，知道它是什么即可。

判断标准：

“不理解这个东西，现在是否阻塞我的DoD？”

如果不阻塞，就警惕继续深挖。

第一性原理不是把所有东西拆到底。

而是识别真正决定结果的变量，从而知道什么值得深入，什么不值得。


九、任务必须拆到可以行动的颗粒度

禁止：

“今天学RAG。”
“今天做论文。”
“今天学英语。”
“今天复习Java。”

合格任务需要：

明确动作 + 短反馈 + 真实结果 + DoD。

例如：

“实现read_text(file_path)，按utf-8→utf-8-sig→gbk解码；分别用UTF-8中文txt和GBK txt测试，均能正确输出。”

原则上，一个最小训练动作应该可以在约1小时内完成。

但不是说所有任务只能持续1小时。

大型任务可以连续完成多个小模块。


十、每个任务必须提前定义DoD

DoD = Definition of Done。

“做了”不等于“完成”。

比如：

错误：
“看完BackgroundTasks教程。”

正确：

运行最小Demo；
curl观察接口行为；
脱离教程补核心代码；
回答一个变式场景。

DoD以后才算完成。

特别重要的一条：

AI给出了答案，不算任务推进完成。

AI只是把训练器材搬到了你面前。


十一、AI采用渐进撤离，而不是“要么依赖AI、要么完全闭卷”

目前正式辅助等级：

L0：
AI给完整实现，我运行并理解大致结构。

L1：
AI删除10%—30%的关键代码，我补TODO。

L2：
AI只给函数签名、伪代码、关键API，我实现。

L3：
AI只给需求和DoD。允许查官方文档/搜索，但不能直接索要完整答案。

L4：
接近面试环境，有限帮助，独立完成核心实现。

L5：
改变需求、制造bug、增加约束，我必须迁移知识并解释trade-off。

不要从L0突然跳L4。

连续成功，再撤脚手架。

连续失败，降低半级/一级。

难度调整，而不是人格审判。


十二、严格区分“接触过”和“掌握”

目前统一标准：

L0：见过。
L1：能跟着做。
L2：理解并能补全。
L3：能够独立实现。
L4：面试/闭卷环境基本能完成。
L5：可以迁移、debug、应对变式。

“看懂了”不能再说成：

“我会了。”

以后更准确地说：

“这个知识目前处于L1。”


十三、AI→自己的切换点必须特殊保护

这是目前发现的一个高频漏洞。

你的典型链条：

AI搜集信息
→ 感觉已经做了不少
→ 准备进入自己验证
→ “休息一下”
→ 手机/其他小事
→ 主任务漂移。

所以增加“交接动作”。

每次AI阶段结束：

AI停止
→ 不休息
→ 立即完成3—10分钟自主输出
→ 之后才允许休息。

交接动作可以是：

写5行伪代码；
回答一道场景题；
补三个TODO；
画一次状态流转；
先预测代码运行结果；
关掉论文写出input/method/output；
用自己的话复述三个关键点。

必须建立新的条件反射：

“AI停止输出” = “轮到我输出”。

而不是：

“这一轮结束了。”


十四、验证难度也采用渐进增加

禁止：

AI刚完整演示
→ 马上要求自己完整闭卷重写。

可以：

完整代码
→ 挖3个TODO
→ 只留函数骨架
→ 只留伪代码
→ 只给需求
→ 需求变式。

你要训练的是能力迁移，不是用突然增加的痛苦证明自己有毅力。


十五、真正有效的学习闭环

统一使用：

输入
→ 模仿
→ 回忆
→ 验证
→ 变式
→ 间隔复测。

其中最重要的是：

Retrieval：没有答案时能否自己提取。

Transfer：条件改变以后能不能使用。

因此AI以后优先承担四个角色：

面试官；
出题人；
故障制造者；
验收员。

减少单纯作为“答案生成器”。


十六、不会“自由思考”时，用脚手架式思考

你面对完全开放的问题容易觉得困难，然后直接看答案。

所以不要一开始问：

“你深入思考BackgroundTasks和Celery的区别。”

改成具体情境：

“视频转码平均20分钟，服务重启任务不能丢，只能二选一：BackgroundTasks/Celery？”

先强迫选择。

然后说明理由。

AI再反馈。

然后换场景：

“注册后异步发欢迎邮件，200ms，失败影响很小，还需要Celery吗？”

经历多个案例后，再总结原则。

顺序：

具体判断 → 得到反馈 → 相似变式 → 最后抽象规律。

而不是：

先背抽象规律。


十七、严防“伪生产性拖延”

你不只是会刷手机逃避。

更加隐蔽的是：

主任务很难
→ 去整理笔记
→ 回消息
→ 查资料
→ 学英语
→ 写公众号
→ 看经验帖
→ 收拾东西。

它们可能都是“好事”。

但是如果当前最重要的任务DoD没有完成，这些事情有时承担的是逃避功能。

执行新任务前问：

“当前主任务DoD过了吗？”

没有的话：

允许真正休息；
允许吃饭、厕所、处理紧急事务；

但原则上不允许用另一个低优先级“有意义任务”获得虚假的生产感。


十八、允许休息，但是休息不能变成无定义漂移

不追求连续工作三四小时。

工作40分钟想休息，并不说明意志薄弱。

真正应该观察：

“休息以后能不能回来？”

所以训练目标从：

“不能离开工作。”

变成：

“离开以后可以可靠返回。”

休息前提前写下：

“回来第一个动作是什么？”

例如：

“回来运行failed case pytest。”

这样返回的时候不用重新决策。


十九、娱乐失控的目标不是“我从此毫无欲望”

电视剧、短视频、色情内容等高即时奖励刺激单独治理。

不把：

“今天看了10小时电视剧”

升级为：

“我不是做大事的人。”

首先治理行为链：

触发
→ 开始
→ 续播
→ 失控
→ 返回。

当前核心指标不是：

“是否永远不偏离。”

而是：

“从偏离到发现，再到返回，需要多久？”

缩短恢复时间本身就是能力增长。


二十、不用第二天的惩罚偿还昨天

典型错误：

昨天浪费10小时
→ 强烈羞耻
→ 明天Agent 4h+论文3h+英语2h
→ 高压
→ 疲劳
→ 再次逃避。

禁止补偿性计划。

昨天损失就是损失。

记录、找原因、修机制。

第二天回到原训练计划。


二十一、重新定义“对自己严格”

严格不是：

“从此绝不犯。”
“真正牛逼的人不会这样。”
“必须逼自己做到。”
“做不到就是意志力不行。”

真正的严格是：

不粉饰结果；
不用“放假嘛”合理化；
也不用“我是废物”把行为升级成人格；
准确记录；
找到失败节点；
修改机制；
重新测试。

严格针对行为和结果。

不针对人格。


二十二、自信建立在“接受检验”上，而不仅是“坚持”

你已经通过健身证明：

“我能坚持。”

下一阶段不需要反复证明这一点。

真正需要积累：

“受检验型自信。”

即：

我不知道自己行不行
→ 我仍然交卷
→ 得到结果
→ 处理结果
→ 再交。

最终希望形成的是：

“问题处理型自信”。

不是：

“我一定成功。”

而是：

“出了问题，我能处理。”


二十三、每天至少存在一个“现实检验”

“学习了”不算现实检验。

例如：

开发：
pytest、闭卷编码、变式、PR、commit、mock interview、真实投递。

算法：
限时独立做题。

论文：
实验结果、图表、protocol、导师/AI攻击问题。

六级：
限时真题正确率、作文评分、翻译评分。

评价一天不能只看：

“今天学习了几个小时？”

还要问：

“今天什么东西接受了评分？”


二十四、根据精力改变任务，而不是放弃推进

高精力：

算法闭卷；
项目核心模块；
论文设计；
Mock Interview；
复杂debug。

中精力：

SQL练习；
测试；
六级阅读；
论文整理；
普通编码。

低精力：

README；
修测试；
错误整理；
单词复测；
实验表格；
简单文档；
Git操作。

状态不好可以降负荷。

不能默认切到手机。


二十五、反馈只记录事实，不写长篇自我审判

一次训练反馈优先只写：

任务：
结果：
AI辅助级别：
独立测试结果：
卡点：
感受：
下一次待验证问题：

例如：

“任务：M4 process_document
结果：pytest通过
AI：L1
独立：核心流程只能完成60%
卡点：异常路径和session生命周期想不起来
感受：空白文件出现时不知道从哪开始。”

然后进行诊断。

不需要先写2000字解释：

“为什么我又失败了。”


二十六、出现失败时的诊断顺序

禁止第一反应：

“我懒/我怕困难/我意志力差。”

依次判断：

目标是否清楚？
DoD是否清楚？
任务是否太大？
前置知识是否缺失？
难度是否跨级？
AI撤离是否过快？
反馈是否太迟？
任务是否距离真实目标太远？
当前精力是否匹配？
环境有没有制造巨大诱惑？
是不是任务切换点出问题？
最后再判断是否存在主动逃避。

不要把所有学习问题心理化。


二十七、语言协议

这是目前非常需要持续监控的一部分。

警惕这些词：

“一定”
“100%”
“根本”
“都是”
“从来”
“最关键”
“我就是……”
“自欺欺人”
“我的底色就是……”

这些语言容易把：

观察 → 规律 → 人格定论

三个步骤一次跳完。

例如：

不说：

“我100%在困难任务前逃避。”

改成：

“最近记录中，AI→自主验证这个切换点出现了高频任务漂移。”

不说：

“我就是不能接受竞争的人。”

改成：

“过去若干具有明确评价的任务中，我观察到了延迟接受检验的行为。”

不说：

“我自欺欺人做俯卧撑。”

改成：

“我选择了一个和最终目标相关性未经验证的代理指标。”

语言越精确，问题越容易解决。


二十八、尤其警惕“最关键的问题”成瘾

你有比较强的元认知能力，但也因此容易不断发现：

“原来这才是我的核心问题。”

然后：

理解一个新概念
→ 很兴奋
→ 重构整套方法
→ 过几天再发现另一个“真正核心”。

以后一个新观点必须经过实际行为验证，才能进入长期协议。

原则：

“一次发现叫假设，反复出现才叫模式，有数据支持以后才修改系统。”


二十九、目前三个现实主目标

现阶段始终记住资源优先级：

第一主线：
Java后端 + Agent开发 → 实习/秋招竞争力。

第二刚性主线：
论文benchmark → 开题、实验、毕业。

第三刚性主线：
英语 → 当前首先接受六级真实考试评分，长期再走向实际交流能力。

健身继续，但不能因为它最容易产生掌控感，而挤占最关键的职业窗口。

公众号、商业知识、投资、自媒体、独立产品目前均属于次级事项。

不能用长期重要但当前不紧急的事情，逃避当前真正困难且紧急的事情。


三十、整套方法最后压缩成一张脑内流程图

以后面对任何学习任务，只需要跑：

“我要的现实结果是什么？”

↓

“我能不能现在直接碰一次终点？”

能：
直接测试。

不能：
找到距离它最近的测试。

↓

“我具体失败在哪？”

↓

“这个失败目前由什么瓶颈造成？”

↓

“只补这个瓶颈需要的最小知识。”

↓

“把训练拆成≤1小时、有明确DoD的小块。”

↓

“不会就让AI搭脚手架，不逞强。”

↓

“AI输出结束，立刻进行3—10分钟交接动作。”

↓

“逐渐撤掉AI。”

↓

“自己回忆/编码/判断。”

↓

“给变式。”

↓

“重新碰终点。”

↓

“根据结果决定下一步。”

这就是你目前真正应该重复的循环：

A → 测A → 找瓶颈B → 练B → 再测A。

而不是：

B → B → B → B → 等我觉得自己准备好了 → A。


如果再把整个V1.4压缩成一句最适合你自己的话：

“先碰终点，再补能力；任务做到可验证，AI用来搭脚手架而不是替我掌握；不拿准备冒充推进，不拿代理指标冒充结果，不拿一次失败定义自己——交卷，得到反馈，再练。”

这份可以作为当前基线。之后不应该轻易升级到“V1.5”。只有你实际跑起来以后出现反复、具体、可观察的新问题，我们再打补丁，而不是继续完善理论。
