






# 数据库模块

使用ThreadLocal存储用户id，实现对公共字段的自动填充；使用Redis缓存菜品数据等，缓解高并发情况下频繁查
询数据库导致性能下降的问题；数据库MySQL主从复制实现读写分离，有效降低数据库压力且提高数据库安全性；使用Nginx
部署静态资源，配置反向代理，配置负载均衡；使用Swagger自动生成接口文档。



# 安全模块

使用Token令牌的登录方式，提高了访问认证速度，实现了Session共享；

使用Redis做了令牌和用户信息的对应管理；

使用ThreadLocal保存用户信息，在请求的线程内，可以随时获取登录的用户并做了线程隔离，多个用户之间不会互相影响，使用完后做了value的删除，防止了内存泄漏。




# 测试模块










完整的**软件研发生命周期**，**10个阶段**
## 全景图（先看一眼全貌）

```
需求 → 设计 → 开发 → 自测 → 代码审查 → 提测 → 测试 → 预发布 → 上线 → 监控
  ↑                                                                       ↓
  └──────────────────────── 反馈循环（持续迭代）───────────────────────────┘
```

---

## 第一阶段：需求阶段

### 做什么
- 产品经理和业务方沟通，明确要做什么
- 输出：**需求文档（PRD）**、**原型图（Figma/Axure）**

### 常见问题 & 解决方法

| 问题          | 表现              | 解决方法                            |
| :---------- | :-------------- | :------------------------------ |
| **需求不明确**   | "做一个像淘宝一样的系统"   | 要求产品经理写**用户故事**（作为XX，我想XX，以便XX） |
| **需求频繁变更**  | 开发到一半，业务方说"改一下" | 建立**需求变更流程**：小改走快速通道，大改走评审会     |
| **多方意见不一致** | 产品、开发、测试各说各话    | 开**需求评审会**，所有角色到场，当场确认          |
| **伪需求**     | 业务方说要A，实际需要的是B  | 追问**"为什么要做这个？"**，找到根本目的         |

> 💡 **核心原则**：需求阶段多花1天，开发阶段省3天。**需求没确认前，不要写一行代码。**

---

## 第二阶段：技术设计/架构设计

### 做什么
- 技术选型（用Java还是Go？MySQL还是PostgreSQL？）
- 数据库设计（ER图）
- 接口设计（API文档）
- 系统架构图（微服务还是单体？）
- 输出：**技术方案文档**、**数据库设计文档**、**接口文档**

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **过度设计** | 就3个用户，搞了微服务+K8s | 遵循**YAGNI原则**（You Aren't Gonna Need It），先做简单，后续再拆 |
| **设计不足** | 没有考虑扩展性，后面改不动 | 至少考虑**未来6个月**的扩展方向 |
| **数据库设计不合理** | 字段冗余、没有索引、分表没考虑 | 提前做**数据量预估**，设计好索引和分表策略 |
| **接口设计不规范** | 返回格式不统一，没有版本号 | 制定**接口规范**（如RESTful或GraphQL标准） |
| **技术选型分歧** | 团队争Java vs Go | 考虑**团队熟悉度 + 生态 + 维护成本**，不要为了技术而技术 |

> 💡 **核心原则**：设计阶段是**试错成本最低**的阶段，多讨论、多评审、多推翻重来都不怕。

---

## 第三阶段：开发

### 做什么
- 按功能拆分成任务（TDD模式：先写测试用例再写代码，还是先写代码再补测试？都可以）
- 写代码、写单元测试
- 本地自测
- 提交代码到Git

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **进度延期** | 预计3天，实际做了7天 | 拆任务时**颗粒度要小**（不超过1天），每天站会同步 |
| **代码质量差** | 变量名乱起、几百行一个函数 | 建立**代码规范**（Checkstyle/Prettier），代码审查环节把关 |
| **依赖阻塞** | 等另一个同事的接口才能继续 | 提前定义好**接口契约**，用**Mock数据**先模拟 |
| **本地跑不起来** | "在我电脑上能跑啊" | 统一开发环境（Docker Compose一键启动） |
| **忘记写测试** | 测试阶段一堆bug | 要求**测试覆盖率**不低于70%，用工具自动检查 |
| **代码冲突频繁** | 多人改同一个文件 | 分支策略：**主干开发**或**Git Flow**，频繁合并主干 |

> 💡 **核心原则**：开发阶段最重要的不是写得快，而是**写得稳**。烂代码的债，后面还起来是10倍成本。

---

## 第四阶段：自测（冒烟测试）

### 做什么
- 开发完成自己测一遍主流程
- 确保**核心功能**能跑通（登录、下单、支付等）
- 输出：自测通过的标志（比如测试报告截图）

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **开发不自测直接提测** | 测试一测就崩溃 | 建立**准入标准**：提测前必须附自测截图，否则打回 |
| **只测了正向流程** | 只测成功场景，没测失败场景 | 列**自测检查清单**，包含正常+异常场景 |
| **环境不一致** | 本地能跑，测试环境报错 | 用**Docker标准化环境**，本地和测试环境完全一致 |

> 💡 **核心原则**：**不自测的代码，不要交给测试团队。** 你的bug浪费的是整个团队的时间。

---

## 第五阶段：代码审查（Code Review）

### 做什么
- 同事/组长审查你的代码
- 检查：逻辑是否正确、代码规范、安全隐患、性能问题
- 工具：GitHub PR、GitLab MR、Gerrit

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **Review流于形式** | "LGTM"（Looks Good To Me）就过了，没仔细看 | 设定**Review检查清单**（逻辑、安全、性能、规范） |
| **Review太慢** | 等了一天没人看 | 规定**4小时内必须Review**，紧急情况建群喊人 |
| **Review变成吵架** | 个人风格之争（用a?b:c还是if-else） | 用**代码规范工具**（Prettier/Checkstyle）解决风格问题，只Review逻辑 |
| **大PR难Review** | 一次提交上千行 | 要求**PR颗粒度小**（一个功能一个PR，不超过300行） |

> 💡 **核心原则**：Code Review不是为了找茬，是为了**互相学习、保证质量**。**有2个以上 Approve 才能合并**。

---

## 第六阶段：提测（转测试）

### 做什么
- 开发把代码合并到测试分支
- 部署到测试环境
- 通知测试团队开始测试

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **提测内容不清** | 测试不知道改了什么、影响了哪些功能 | 写**提测单**：包含改动点、影响范围、注意事项 |
| **提测后还频繁改代码** | 测试过程中开发不断塞新代码 | 建立**代码冻结期**：进入测试后，只有紧急bug才能改 |
| **测试环境部署失败** | 依赖没配好、配置项漏了 | 使用**自动化部署**（CI/CD），一键部署，减少人为失误 |

---

## 第七阶段：测试

### 做什么
- **功能测试**：逐条验证需求是否实现
- **回归测试**：确保新功能不影响老功能
- **集成测试**：多个系统联调
- **性能测试**：并发、响应时间
- **安全测试**：SQL注入、XSS等
- **兼容性测试**：不同浏览器/手机型号

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **测试时间被压缩** | 开发延期，压缩测试时间 | 砍需求也不能砍测试，**测试时间占整个周期的30-40%** |
| **测试用例覆盖不全** | 漏测线上出bug | **测试用例Review**，产品和开发一起确认 |
| **环境问题干扰测试** | 测着测着环境挂了 | 测试环境**专人维护**，出了问题快速修复 |
| **bug反复出现** | 修复后又复发 | **根因分析**，找到根本原因，不是表面修复 |
| **性能测试没做** | 上线后被高并发打垮 | 上线前必须做**压力测试**，知道系统极限在哪 |
| **测试用例不更新** | 需求改了，测试用例没跟着改 | 需求和测试用例**同步更新**，用工具管理（如Jira + TestRail联动） |

> 💡 **核心原则**：测试团队不是给开发擦屁股的，是**最后一堵墙**。尊重测试，信任测试。

---

## 第八阶段：预发布环境验证

### 做什么
- 在**与生产环境完全一致**的环境上做最后验证
- 执行**回归测试集**（确保没引入新bug）
- 检查配置项、数据库变更脚本
- 输出：**上线审批单**

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **预发环境和生产环境不一致** | 配置不同、数据库版本不同 | 用**Infrastructure as Code（IaC）**（如Terraform）保证环境一致 |
| **数据库变更没提前准备** | 上线时才发现要加字段、迁移数据 | 数据库变更**提前准备**（写迁移脚本），评审通过再执行 |
| **回滚预案没准备** | 上线出问题不知道怎么回滚 | 准备**回滚方案**（代码回滚+数据库回滚+流量切换） |

> 💡 **核心原则**：预发布环境是**上线前的最后一道关卡**，在这里发现问题比在生产上发现问题好一万倍。

---

## 第九阶段：上线

### 做什么
- 执行发布计划（灰度发布/蓝绿部署/分批发布）
- 观察监控指标（CPU、内存、QPS、错误率）
- 业务验证（核心功能快速测一遍）

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **上线失败/回滚** | 代码有问题需要回退 | **灰度发布**（先放量5%，稳定后再全量），出问题立刻切回旧版本 |
| **数据库变更导致回滚困难** | 加了个字段，回滚要删数据 | 数据库变更**向前兼容**（加字段不删字段，回滚时旧代码也能跑） |
| **依赖服务未同步升级** | A服务升级了，B服务没升级 | 梳理**依赖关系图**，提前协调所有依赖方 |
| **上线时间拖延到深夜** | 白天不敢上，只能凌晨 | 建立**自动化上线流程** + **完善的监控告警**，做到白天也能灰度发布 |
| **上线后没人盯着** | 上了就不管了 | 建立**上线值班制度**，前1小时专人盯监控 |
| **回滚时数据不一致** | 新数据写入了，回滚后读不到 | 设计**可回滚的数据结构**（如软删除、保留历史记录） |
| **上线失败责任不清** | 开发、测试、运维互相推诿 | 建立**上线事故复盘机制**（事后回顾，不追责，找根因） |
| **上线审批流卡住** | 等审批人等半天 | 优化审批流程，重要变更提前沟通，不要卡在最后一刻 |

> 💡 **核心原则**：上线不是结束，是**开始**。上线后的24小时决定这个版本成败。

## 第十阶段：监控与反馈

### 做什么
- **系统监控**：CPU、内存、磁盘、网络、GC
- **业务监控**：订单量、支付成功率、注册量
- **日志监控**：错误日志、慢查询日志
- **告警**：配置阈值，异常时自动通知

### 常见问题 & 解决方法

| 问题 | 表现 | 解决方法 |
| :--- | :--- | :--- |
| **监控没配全** | 上线后才发现漏了关键指标 | 上线前检查**监控清单**（系统+业务+日志三个维度） |
| **告警太多像狼来了** | 天天报警，没人当真 | 优化告警策略：**分P0/P1/P2级别**，P0才短信/电话 |
| **日志打得太少** | 出问题时没有日志可查 | 关键路径打**结构化日志**（JSON格式），包含trace_id方便链路追踪 |
| **不知道什么时候该扩缩容** | 流量来了扛不住 | 配置**自动扩缩容**（HPA），或者制定**扩容预案** |
| **用户反馈渠道不畅通** | 用户遇到问题不知道找谁 | 建立**用户反馈群**或**在线客服**，快速响应用户 |


> 💡 **核心原则**：**没有监控的上线就是裸奔**。你需要在用户发现问题之前自己先发现。

## 四、最后的建议

如果你是**一个人**全包，不需要学所有技术，按这个路径进阶：

1. **前期（0-1阶段）**：熟悉代码 + 数据库 + Git + 基本的测试工具（能用Postman测接口）
2. **中期（团队协作）**：加上 CI/CD（至少能用 GitHub Actions 自动打包）+ Docker（打包部署）+ 基本的监控（能看日志和错误）
3. **后期（上量后）**：加上 Kubernetes（容器编排）+ 链路追踪 + 性能压测 + 告警机制

一步一步来，**不要一次性全学**。遇到什么问题，再针对性地补对应环节的技术。

> 💡 **关键思维**：工具是服务流程的，不是反过来。先理解流程需要什么，再去学对应的工具，比盲目学工具再找场景效率高得多。
