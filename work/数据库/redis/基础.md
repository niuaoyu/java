# **持久化策略RDB AOF**

从最后一次成功生成RDB快照开始，到Redis宕机之间发生的数据修改，如果没有AOF记录，就可能丢失。

Redis 的持久化主要有两种：

1. **RDB（Redis Database）快照**： 定期拍照，把内存数据保存下来。
2. **AOF（Append Only File）追加日志**：记录每一次写操作，重启时重新读取appendonly.aof执行这些操作。

RDB：定期fork主进程，来执行写操作，主进程不影响正常工作，保存到dump.rdb文件
使用了Copy On Write（写时复制）

COW，Copy On Write（写时复制）的核心就是：**不在原地修改，而是复制后修改！**
✅ COW的真相：物理内存地址级别的复制

1️⃣ **详细的内存地址变化** 

```
【初始状态 - fork后】
物理内存地址：0x1000
数据：key="user:1" value="Alice"
    ↑                    ↑
主进程页表[0]        子进程页表[0]
(指向0x1000)        (指向0x1000)


【主进程修改 key="user:1" → "Bob"】

Step 1: 主进程尝试写入0x1000
        → 触发页错误（Page Fault）
        → 因为这页被标记为只读！

Step 2: 操作系统介入
        → 在新地址0x2000分配一页
        → 复制0x1000的内容到0x2000
        → 在0x2000上修改数据为"Bob"

Step 3: 更新主进程页表
        主进程页表[0] → 0x2000 ✅

【结果】
物理地址0x1000: "Alice" ← 子进程继续读这里
物理地址0x2000: "Bob"   ← 主进程现在读写这里

主进程页表[0] → 0x2000
子进程页表[0] → 0x1000

物理内存里有两份数据，指向不同地址！
```

2️⃣ **图解：物理内存布局** 📊

```
fork后立即：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 主进程和子进程都指向这里
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
└─────────────────────────┘

主进程修改user:1后：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 子进程仍指向这里 ✅
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
│ 0x2000: user:1=Bob     │ ← 主进程现在指向这里 ✅（新复制的页）
└─────────────────────────┘
```
实际COW机制：
```
✅ 正确场景：
物理地址0x1000: "Alice" → 保持不变
物理地址0x2000: "Bob"   → 新分配的页
子进程读0x1000 → 读到"Alice" → RDB快照一致 ✅
```

**问题1：dump.rdb最终保存的是这10GB内存数据吗？**

✅ **是的！** 子进程遍历的是fork瞬间的**完整快照**，即使主进程后续修改了数据，子进程读到的仍是旧值，所以dump.rdb保存的是fork时刻的10GB数据
    

**问题2：物理内存被修改，子进程也读到新数据？**

❌ **不是！** 因为：主进程修改时，**不在原物理地址修改**，而是**复制到新地址再修改**，子进程的页表仍指向旧地址，所以子进程读到的始终是旧数据
```
初始：10GB
fork后：10GB（共享）
RDB期间写入1GB数据：
  → 复制1GB到新地址
  → 总内存：10GB原始 + 1GB新副本 = 11GB
  → 不是 10GB + 10GB = 20GB ✅
```

- COW = Copy（复制到新地址） + On Write（写时才复制），这里的写时才复制是对主进程说的，复制到新地址也是对于主进程说的。
- 旧物理页保持不变，子进程继续安全读取，新物理页给主进程使用，两个进程操作**不同的物理内存地址** 🔑，这就是为什么叫"Copy-On-Write"，而不是"Modify-In-Place"！✨


RDB和AOF区别

|      | RDB      | AOF            |
| ---- | -------- | -------------- |
| 方式   | 数据快照     | 记录命令           |
| 文件   | dump.rdb | appendonly.aof |
| 恢复速度 | 快        | 慢              |
| 数据安全 | 低        | 高              |
| 文件大小 | 小        | 大              |
| 性能影响 | 小        | 稍大             |
| 适合   | 备份       | 高可靠            |


如果面试问：Redis持久化怎么实现？

> Redis提供RDB和AOF两种持久化方式。RDB通过fork子进程生成内存快照文件dump.rdb，利用Copy On Write保证主线程继续处理请求；AOF通过记录每次写命令到appendonly.aof文件，Redis重启时重新执行这些命令恢复数据。RDB恢复快但可能丢失部分数据，AOF数据安全性更高但文件更大，实际生产一般两者结合使用。

这就是 Redis 持久化的核心原理。




# 缓存穿透


什么是缓存穿透？查询一个**数据库中不存在**的数据，因为缓存也没有，所以每次请求都会"穿透"缓存，直接打到数据库上。
```
【正常查询流程✅】
用户查询 user:1000
  → Redis查询 → 命中 → 返回数据
  
或者
  → Redis查询 → 未命中 
  → MySQL查询 → 找到数据 
  → 写入Redis → 返回数据


【缓存穿透❌】
恶意用户查询 user:-1（不存在）
  → Redis查询 → 没有
  → MySQL查询 → 也没有
  → 不缓存（因为是空结果）
  → 返回null

下次再查 user:-1
  → Redis查询 → 还是没有
  → MySQL查询 → 又查一次
  → 无限循环... 💥
```
黑客就可以攻击了

```
【攻击场景】
黑客脚本：
for i in range(-1, -100000):
    requests.get(f"/api/user/{i}")

结果：
- 100万个不存在的ID
- 每个请求都打到MySQL
- MySQL瞬间被打崩 💥
- Redis完全失去保护作用
```
解决办法
1. **缓存空对象**：即使数据不存在，也在Redis中缓存一个空值，简单高效保护数据库，但会占用redis内存（大量的没用的key）
2. **参数校验** ： 在业务层拦截明显非法的请求，不正确的直接不给你查数据库的机会
3. 限流：最好理解
4. 布隆过滤器（Bloom Filter）：在Redis之前加一层布隆过滤器，快速判断数据是否可能存在。好处是 ✅ 内存占用极小（10亿数据只需约1.2GB）✅ 查询速度极快（O(k)，k为哈希函数个数）✅ 适合海量数据，坏处❌ 存在误判（可能存在的数据，实际不存在，但概率可控），❌ 删除困难（标准布隆过滤器不支持删除）

**核心思想：** 

```java
// 初始化布隆过滤器
@PostConstruct
public void initBloomFilter() {
    // 预计1000万数据，误判率0.01%
    BloomFilter<Long> bloomFilter = 
        BloomFilter.create(Funnels.longFunnel(), 10000000, 0.0001);
    
    // 将所有用户ID加入布隆过滤器
    List<Long> userIds = userMapper.selectAllIds();
    for (Long id : userIds) {
        bloomFilter.put(id);
    }
}

public User getUserById(Long id) {
    // 1. 布隆过滤器判断
    if (!bloomFilter.mightContain(id)) {
        return null; // 一定不存在，直接返回 ✅
    }
    
    // 2. 可能存在，继续查Redis
    String key = "user:" + id;
    String json = redis.get(key);
    if (json != null) {
        return JSON.parseObject(json, User.class);
    }
    
    // 3. 查数据库
    User user = userMapper.selectById(id);
    if (user != null) {
        redis.setex(key, 3600, JSON.toJSONString(user));
    }
    return user;
}
```

**Redis实现（使用Redisson）：**

```java
@Autowired
private RedissonClient redisson;

public void initBloomFilter() {
    RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
    bloomFilter.tryInit(10000000L, 0.0001); // 初始化
    
    // 添加所有存在的ID
    List<Long> userIds = userMapper.selectAllIds();
    for (Long id : userIds) {
        bloomFilter.add(id);
    }
}

public User getUserById(Long id) {
    RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
    if (!bloomFilter.contains(id)) {
        return null; // 快速拦截 🚫
    }
    // ... 后续逻辑
}
```

|方案|适用场景|内存占用|实现复杂度|效果|
|---|---|---|---|---|
|缓存空对象|小规模攻击|中|⭐ 简单|中|
|布隆过滤器|海量数据|低|⭐⭐⭐ 中等|高|
|参数校验|配合使用|无|⭐ 简单|低|
|限流|防止暴力攻击|低|⭐⭐ 简单|中|
实际生产方案 **推荐组合拳：**
```java
@Service
public class UserService {
    
    @Autowired
    private RedissonClient redisson;
    
    @Autowired
    private StringRedisTemplate redis;
    
    // 1. 参数校验 + 2. 布隆过滤器 + 3. 缓存空对象
    @RateLimiter(name = "getUser", permitsPerSecond = 1000)
    public User getUserById(Long id) {
        // ① 参数校验
        if (id == null || id <= 0 || id > 10000000) {
            throw new IllegalArgumentException("Invalid id");
        }
        
        // ② 布隆过滤器
        RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
        if (!bloomFilter.contains(id)) {
            return null; // 一定不存在 🚫
        }
        
        // ③ 查Redis
        String key = "user:" + id;
        String json = redis.opsForValue().get(key);
        
        if (json != null) {
            return "NULL".equals(json) ? null : JSON.parseObject(json, User.class);
        }
        
        // ④ 查数据库
        User user = userMapper.selectById(id);
        
        // ⑤ 缓存结果（包括空对象）
        if (user == null) {
            redis.opsForValue().set(key, "NULL", 60, TimeUnit.SECONDS);
        } else {
            redis.opsForValue().set(key, JSON.toJSONString(user), 
                                    30, TimeUnit.MINUTES);
        }
        
        return user;
    }
}
```


**缓存穿透 = 查询不存在的数据，导致请求穿透缓存打到数据库**

**解决方案优先级：**

1. **必选：** 参数校验 + 限流（第一道防线）
2. **推荐：** 布隆过滤器（海量数据场景）
3. **备选：** 缓存空对象（小规模场景）

**核心原则：** 多层防护，从外到内逐层拦截恶意请求！


# 缓存击穿

什么是缓存击穿？简单说，热点key（如热门商品）过期瞬间，大量并发请求同时打到数据库。
```
【正常情况✅】
热点商品 product:1001 在Redis中
1000个并发请求 → Redis返回 → 数据库无压力

【缓存击穿❌】
晚上12点，product:1001过期
同一瞬间1000个请求到达：
  → Redis查询 → 都miss了
  → 1000个请求全打到MySQL
  → 数据库瞬间压力暴增 💥
```

**缓存击穿 vs 缓存穿透的区别**

|维度|缓存穿透|缓存击穿|
|---|---|---|
|数据|**不存在**的数据|**存在**但过期的热点数据|
|频率|持续发生|**瞬间**爆发|
|影响|所有不存在的key|**单个**热点key|
解决方案 🛡️
1. **互斥锁（最常用）** ：1000个并发请求到达 → key已过期
	1. ├─ 线程1：抢到锁 → 查DB → 写缓存 ✅
	2. └─ 线程2-1000：等待 → 重试 → 命中缓存 ✅
	3. 只有1个请求打到数据库！
2. **永不过期** （逻辑过期）：Redis里的数据**永远不删除**，但在数据里**自己记录一个过期时间**
3. 物理永不过期：Redis里的key根本**不设置过期时间**，由后台定时任务主动刷新。
4. **提前预热** ：在用户访问高峰**之前**，先把热点数据加载到Redis。

## **逻辑过期** 🧠

### 核心思想

Redis里的数据**永远不删除**，但在数据里**自己记录一个过期时间**。
### 详细流程
```
【存储的数据结构】
Key: product:1001
Value: {
    "data": {商品信息},
    "expireTime": 1234567890  ← 自己记录的过期时间戳
}
Redis TTL: 永不过期 ♾️


【查询流程】
用户查询 product:1001
  ↓
从Redis读到数据（一定能读到，因为永不删除）
  ↓
检查里面的expireTime字段
  ↓
如果 expireTime < 当前时间：
  ├─ 判定"逻辑上已过期"
  ├─ 启动后台线程去更新数据库
  └─ 但先把旧数据返回给用户 ✅（关键！）
  
后台线程：
  └─ 查数据库 → 更新Redis里的数据和expireTime
  
下次用户来查：就是新数据了


【为什么有效？】
- 1000个并发来了，都能从Redis读到数据（虽然是旧的）
- 只有第1个请求触发后台更新
- 其他999个请求直接返回旧数据
- 数据库只被访问1次 ✅
```

**白话：**  
就像牛奶过期了，但没扔掉。你看到过期了，先喝这盒旧的（还能喝），同时叫人去买新的。下次再来就有新牛奶了。🥛


## **物理永不过期** ♾️

### 核心思想

Redis里的key根本**不设置过期时间**，由后台定时任务主动刷新。

### 详细流程

```
【初始化】
商品1001上线 → 写入Redis
redis.set("product:1001", {商品数据})  ← 注意：没有设置TTL


【查询】
用户查询 → 从Redis读 → 返回
（永远能读到，因为key永不过期）


【更新机制】
后台定时任务（每30分钟运行一次）：
  ↓
找出所有热点商品ID
  ↓
逐个查数据库
  ↓
更新Redis里的数据

比如：
11:30 → 更新一次
12:00 → 更新一次
12:30 → 更新一次
...


【为什么有效？】
- Redis里永远有数据
- 没有"过期瞬间大量请求打DB"的问题
- 数据库访问被分散到定时任务里
```

**白话：**  
就像家里冰箱的牛奶，不是等喝完再买，而是每周固定时间去超市补货。冰箱里永远有奶。🛒

## 方案3：**提前预热** 🔥

### 核心思想

在用户访问高峰**之前**，先把热点数据加载到Redis。

### 详细流程

```
【场景：双11活动】
活动时间：11月11日 00:00 开始
预计会有秒杀商品被疯狂查询


【预热操作】
11月10日 23:50（活动前10分钟）：
  ↓
运行预热脚本
  ↓
找出所有秒杀商品（比如100个）
  ↓
逐个查数据库
  ↓
写入Redis，设置较长过期时间（比如2小时）
  ↓
完成预热 ✅


【活动开始】
00:00 用户蜂拥而至
  ↓
所有请求都命中Redis
  ↓
数据库无压力 ✅


【为什么有效？】
- 在高峰前数据已经在Redis里了
- 不存在"过期瞬间"的问题
- 避免了冷启动
```

**白话：**  
就像演唱会开场前，先把饮料贩卖机装满。等观众来了，直接买就行，不用现场去仓库搬货。🎤

## 三者对比 📊

|方案|比喻|核心机制|数据新鲜度|
|---|---|---|---|
|逻辑过期|过期牛奶先喝，同时买新的|返回旧数据，异步更新|短暂陈旧|
|物理永不过期|定期补货|定时任务主动刷新|可能陈旧|
|提前预热|活动前装满货架|高峰前预加载|最新 ✅|

### 逻辑过期

```
适合：超高并发场景
比如：淘宝首页推荐商品
- 1秒10万次查询
- 允许短暂返回稍旧的数据
- 不能让数据库扛10万QPS
```

### 物理永不过期

```
适合：极热点且变化不频繁
比如：微博热搜榜单
- 每分钟刷新一次就够了
- 不需要实时精确数据
- 避免突然过期的风险
```

### 提前预热

```
适合：可预测的流量高峰
比如：
- 秒杀活动（11:00开始，10:55预热）
- 世界杯直播（开赛前5分钟预热）
- 新品发布会（发布前预热）
```


1. **逻辑过期** = 数据在Redis里永久存着，但标记"过期时间"，过期了返回旧的同时异步更新新的 🔄
2. **物理永不过期** = Redis的key不设置过期，后台定时任务定期刷新所有热点数据 ⏰
3. **提前预热** = 高峰来之前，把热点数据提前塞进Redis ⏰
    

|方案|优点|缺点|适用场景|
|---|---|---|---|
|互斥锁|实现简单，只有1个DB请求|有等待时间|通用 ✅|
|逻辑过期|无等待，性能高|返回旧数据，实现复杂|超高并发|
|物理永不过期|简单|占用内存，可能数据陈旧|极热点数据|
|提前预热|完全避免问题|需预知热点|活动场景|

**缓存击穿 = 热点key过期，瞬间大量请求打到DB**

**最佳实践：**

- 🥇 **首选：互斥锁**（简单有效）
- 🥈 **次选：逻辑过期**（极高并发）
- 🥉 **辅助：提前预热**（活动场景）
    
**一句话：用锁保证只有一个请求去查数据库，其他请求等待或重试！** 
**共同点：都是为了避免"key过期瞬间，大量请求同时打到数据库"！** 



# 缓存雪崩

什么是缓存雪崩？💥**一句话定义：**  大量key在**同一时间**集体过期，导致所有请求瞬间打到数据库。
```
【正常情况✅】
product:1  (12:00过期)
product:2  (12:05过期)
product:3  (12:10过期)
过期时间分散 → 数据库压力平稳


【缓存雪崩❌】
批量导入1000个商品，都设置1小时过期
12:00:00 全部写入Redis
13:00:00 1000个key同时过期 💥
  ↓
此时10万个并发请求到达
  ↓
全部打到数据库
  ↓
数据库直接崩溃 💀
```

### vs 缓存击穿的区别

|维度|缓存击穿|缓存雪崩|
|---|---|---|
|影响范围|**单个**热点key|**大量**key|
|原因|1个key过期|大批量key**同时**过期|
|后果|DB压力激增|DB**直接崩溃** 💀|

解决方案 🛡️
1. **过期时间加随机值（最常用）** 🎲：让key的过期时间错开，不要集体过期

```

**效果：**

```
原本：13:00:00 全部过期 → 瞬间DB压力100%

现在：
13:00:00 ~ 13:05:00 逐渐过期
每秒过期20个key，而不是一次过期1000个
DB压力从"尖峰"变成"缓坡" ✅
```

---

### 方案2：**永不过期** ♾️

**两种实现：**

#### 物理永不过期

```
写入时不设置TTL：
redis.set("product:1", data);  // 没有过期时间

优点：永远不会雪崩
缺点：数据可能陈旧，占用内存
适合：热点数据，如首页banner
```

#### 逻辑过期

```
数据结构：
{
    "data": 商品信息,
    "expireTime": 时间戳  ← 自己记录过期时间
}

过期后：
- 返回旧数据（先顶着用）
- 后台异步更新

优点：避免雪崩，用户无感知
缺点：可能返回稍旧数据
```

---

### 方案3：**多级缓存** 🏗️

**核心思想：** 不要只依赖Redis，建立多层防护

```
【架构层次】
用户请求
  ↓
本地缓存（JVM内存，Caffeine）  ← 第1层
  ↓ miss
Redis                          ← 第2层
  ↓ miss
数据库                         ← 第3层


【雪崩发生时】
Redis全部过期
  ↓
但本地缓存还有数据
  ↓
大部分请求被本地缓存拦住
  ↓
只有少量请求打到DB ✅
```

**实现：**

```
查询流程：
1. 查本地缓存 → 命中返回
2. 查Redis → 命中返回 + 写本地缓存
3. 查DB → 返回 + 写Redis + 写本地缓存

即使Redis雪崩，本地缓存也能扛一阵子
```

---

### 方案4：**Redis集群 + 主从 + 哨兵** 🏰

**核心思想：** 避免Redis服务整体挂掉

```
【单点Redis】
Redis崩溃 → 所有数据丢失 → 缓存雪崩


【集群方案】
Redis主节点挂了
  ↓
哨兵自动切换到从节点
  ↓
服务继续 ✅

Redis Cluster：
- 数据分片存储
- 某个分片挂了，只影响部分数据
- 不会全盘雪崩
```

---

### 方案5：**限流降级** 🚦

**核心思想：** 雪崩时保护数据库，宁可拒绝部分请求

```
【限流】
数据库最多扛1000 QPS
  ↓
设置限流：超过1000 QPS直接返回降级响应
  ↓
保证DB不被打死


【降级】
检测到DB压力过大
  ↓
返回默认数据或提示：
"系统繁忙，请稍后再试"
  ↓
牺牲部分用户体验，保住系统存活 ✅
```

---

### 方案6：**提前预热** 🔥

**核心思想：** 重启后先预热，避免冷启动雪崩

```
【不预热的问题】
Redis重启 → 缓存全空
  ↓
流量进来 → 全打到DB
  ↓
雪崩 💥


【预热流程】
Redis重启后：
1. 阻止流量进入（设置维护模式）
2. 后台脚本批量加载热点数据到Redis
3. 预热完成后再开放流量
4. 流量逐步放开（而不是一次性全放）

避免冷启动雪崩 ✅
```

## 三大缓存问题总结 🎯

|问题|原因|影响范围|核心解决方案|
|---|---|---|---|
|缓存穿透|查询**不存在**的数据|持续影响|布隆过滤器 🌸|
|缓存击穿|**单个热点key**过期|瞬间爆发|互斥锁 🔒|
|缓存雪崩|**大量key同时**过期|系统崩溃|过期时间+随机值 🎲|

**一句话记住缓存雪崩：**  
**大批量key集体过期，错开过期时间是王道！** ❄️✨
