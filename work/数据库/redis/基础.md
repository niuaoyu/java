**持久化策略RDB AOF**

从最后一次成功生成RDB快照开始，到Redis宕机之间发生的数据修改，如果没有AOF记录，就可能丢失。

Redis 的持久化主要有两种：

1. **RDB（Redis Database）快照**： 定期拍照，把内存数据保存下来。
2. **AOF（Append Only File）追加日志**：记录每一次写操作，重启时重新执行这些操作。

RDB：定期fork主进程，来执行写操作，主进程不影响正常工作，保存到dump.rdb文件
使用了Copy On Write（写时复制）


COW，Copy On Write（写时复制）的核心就是：**不在原地修改，而是复制后修改！**
✅ COW的真相：物理内存地址级别的复制

### 1️⃣ **详细的内存地址变化** 

```
【初始状态 - fork后】
物理内存地址：0x1000
数据：key="user:1" value="Alice"
    ↑                    ↑
主进程页表[0]        子进程页表[0]
(指向0x1000)        (指向0x1000)


【主进程修改 key="user:1" → "Bob"】

Step 1: 主进程尝试写入0x1000
        → 触发页错误（Page Fault）
        → 因为这页被标记为只读！

Step 2: 操作系统介入
        → 在新地址0x2000分配一页
        → 复制0x1000的内容到0x2000
        → 在0x2000上修改数据为"Bob"

Step 3: 更新主进程页表
        主进程页表[0] → 0x2000 ✅

【结果】
物理地址0x1000: "Alice" ← 子进程继续读这里
物理地址0x2000: "Bob"   ← 主进程现在读写这里

主进程页表[0] → 0x2000
子进程页表[0] → 0x1000

物理内存里有两份数据，指向不同地址！
```

### 2️⃣ **图解：物理内存布局** 📊

```
fork后立即：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 主进程和子进程都指向这里
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
└─────────────────────────┘

主进程修改user:1后：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 子进程仍指向这里 ✅
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
│ 0x2000: user:1=Bob     │ ← 主进程现在指向这里 ✅（新复制的页）
└─────────────────────────┘
```
实际COW机制：
```
✅ 正确场景：
物理地址0x1000: "Alice" → 保持不变
物理地址0x2000: "Bob"   → 新分配的页
子进程读0x1000 → 读到"Alice" → RDB快照一致 ✅
```


### 5️⃣ **回答你的问题** 🎯

**问题1：dump.rdb最终保存的是这10GB内存数据吗？**

✅ **是的！** 子进程遍历的是fork瞬间的**完整快照**，即使主进程后续修改了数据，子进程读到的仍是旧值，所以dump.rdb保存的是fork时刻的10GB数据
    

**问题2：物理内存被修改，子进程也读到新数据？**

❌ **不是！** 因为：

- 主进程修改时，**不在原物理地址修改**
    
- 而是**复制到新地址再修改**
    
- 子进程的页表仍指向旧地址
    
- 所以子进程读到的始终是旧数据
    

### 6️⃣ **实际验证** 🔬

```bash
# 模拟场景
127.0.0.1:6379> SET user:1 Alice
127.0.0.1:6379> BGSAVE
Background saving started

# 立即修改数据
127.0.0.1:6379> SET user:1 Bob

# 等RDB完成后查看dump.rdb
$ redis-cli --rdb dump.rdb
# 会看到 user:1=Alice（不是Bob！）

# 当前Redis内存中
127.0.0.1:6379> GET user:1
"Bob"
```

### 7️⃣ **内存开销分析** 📈

```
初始：10GB
fork后：10GB（共享）
RDB期间写入1GB数据：
  → 复制1GB到新地址
  → 总内存：10GB原始 + 1GB新副本 = 11GB
  → 不是 10GB + 10GB = 20GB ✅
```

## 总结 🎯

|你的理解|实际机制|
|---|---|
|❌ 物理内存原地修改|✅ 复制到新物理地址再修改|
|❌ 子进程读到新数据|✅ 子进程读旧地址，读到旧数据|
|✅ dump.rdb是10GB快照|✅ 正确！|

**核心理解：**

- COW = Copy（复制到新地址） + On Write（写时才复制）
    
- 旧物理页保持不变，子进程继续安全读取
    
- 新物理页给主进程使用
    
- 两个进程操作**不同的物理内存地址** 🔑
    

这就是为什么叫"Copy-On-Write"，而不是"Modify-In-Place"！✨


fork之后：

# 二、AOF（追加日志）

## 思想

Redis每执行一个写命令：

记录下来。

例如：

客户端：

```redis
SET name mao
```

AOF：

记录：

```
SET name mao
```

然后：

```redis
INCR age
```

AOF：

```
SET name mao
INCR age
```

文件：

```
appendonly.aof
```

---

## AOF怎么恢复？

Redis启动：

读取：

```
appendonly.aof
```

然后：

重新执行：

```
SET name mao

INCR age
```

恢复数据。

类似：

MySQL binlog。

```
 ↓
```

★★★★★

速度最快。

风险最大。

# 六、面试简单回答

如果面试问：

> Redis持久化怎么实现？

可以回答：

> Redis提供RDB和AOF两种持久化方式。RDB通过fork子进程生成内存快照文件dump.rdb，利用Copy On Write保证主线程继续处理请求；AOF通过记录每次写命令到appendonly.aof文件，Redis重启时重新执行这些命令恢复数据。RDB恢复快但可能丢失部分数据，AOF数据安全性更高但文件更大，实际生产一般两者结合使用。

这就是 Redis 持久化的核心原理。
