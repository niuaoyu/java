**Redis怎么解决并发竞争问题（Race Condition）**

比如，三个线程同时操作一个账户，如果有10000，分别取8000，4000,1000都通过了，但是账户最后还变成-3000，这种情况怎么处理的？

主要有4种方案。
1. 

# 方案1：Redis原子命令（最常用）

不要：

```java
get

判断

decr
```

改成：

Lua脚本。

例如：

```lua
local balance =
redis.call('get','balance')

if tonumber(balance)>=8000 then

 redis.call('decrby','balance',8000)

 return 1

else

 return 0

end
```

Redis执行：

```
读取余额
判断
扣钱
```

三个步骤不可分割。

为什么？

因为Lua脚本：

> Redis单线程执行

执行期间：

别人无法插入。

于是：

线程A：

```
余额10000
扣8000
余额2000
```

线程B：

```
余额2000
扣4000失败
```

线程C：

```
余额2000
扣1000
余额1000
```

最终：

```
余额1000
```

正确。

# 方案2：WATCH乐观锁

Redis提供：

```redis
WATCH balance

GET balance

MULTI

DECRBY balance 8000

EXEC
```

流程：

WATCH：

```
监听balance
```

如果别人修改：

```
EXEC失败
```

重新尝试。

类似：

MySQL：

```
version字段
```

例如：

表：

|id|money|version|
|---|---|---|
|1|10000|1|

更新：

```sql
update account

set money=2000,
version=2

where id=1

and version=1
```

# 7. 你这个扣余额问题，实际项目怎么设计？

比如支付系统：

不要：

```
Redis余额
```

而是：

```
用户支付请求
       |
       v
Redis预扣库存/防重复
       |
       v
MQ
       |
       v
MySQL事务扣余额
       |
       v
更新Redis缓存
```

MySQL：

```sql
begin;

select balance
from account
where id=1
for update;


update account
set balance=balance-8000
where id=1;


commit;
```

数据库行锁保证：

三个线程：

```
A拿锁
扣8000
提交


B拿锁
发现2000
失败


C拿锁
扣1000
成功
```

## 总结一句话：

> Redis不是“不安全”，而是不负责强一致业务。Redis适合高性能、低延迟、高并发场景；涉及余额、订单、库存最终一致性的核心数据，通常使用MySQL等数据库，Redis负责缓存、加速和削峰。

你举的“10000被扣成-3000”的问题，本质不是 Redis 事务问题，而是**检查余额 + 扣余额不是一个原子操作**，用 **Lua脚本、WATCH、锁、或者交给数据库行锁**解决。
