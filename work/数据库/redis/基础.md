
Redis 追求：极致性能 + 简单模型
回滚意味着Redis必须记录：修改前的数据、操作日志、依赖关系、恢复逻辑
想要安全，用关系型数据库


redis不保证事务的原子性（没有回滚），中间出错，后续命令继续执行，尽管够快，但这不安全，这怎么处理的？那什么情况适合用redis数据库？




**Redis怎么解决并发竞争问题（Race Condition）**

比如，三个线程同时操作一个账户，如果有10000，分别取8000，4000,1000都通过了，但是账户最后还变成-3000，这种情况怎么处理的？

主要有4种方案。
1. 原子命令：Redis单线程执行Lua脚本，一个线程执行，别的线程插不进来
2. WATCH乐观锁：监听要修改的数据，如果别人修改，那么执行失败重新执行
3. 分布式锁：操作前加锁，我操作完之后，别人再操作，适合lua脚本不方便使用的时候
4. 重要的数据不用redis做账本！！！：redis通常目的是缓存，热点数据，临时状态
	1. 用户支付—Redis判断库存—MySQL扣余额—Redis删除缓存


# 5. 那Redis到底适合什么？

Redis适合：

## ① 缓存

最经典：

```
MySQL
  |
Redis
  |
用户
```

例如：

商品详情：

```
redis.get(product:100)
```

没有：

查数据库

然后：

```
redis.set()
```

---

## ② 计数器

例如：

点赞：

```
INCR article:100:like
```

浏览量：

```
INCR pv
```

因为：

INCR是原子的。

---

## ③ 分布式锁

例如：

秒杀：

```
SET order_lock userId NX EX 5
```

---

## ④ 秒杀库存

例如：

商品：

```
stock=100
```

Redis：

```redis
DECR stock
```

速度非常快。

但是最终：

订单落库：

MySQL。

---

## ⑤ Session共享

集群：

```
服务器A

服务器B

服务器C
```

用户登录：

session存Redis。

---

## ⑥ 消息队列（简单场景）

例如：

```
List

LPUSH

BRPOP
```

# 6. Redis和MySQL事务能力区别

||Redis|MySQL|
|---|---|---|
|事务|弱事务|强事务|
|回滚|❌|✅|
|ACID|部分满足|完整|
|速度|极快|较慢|
|复杂查询|❌|✅|
|资金数据|❌|✅|
|缓存|✅|❌|
|高并发计数|✅|一般|

---

> Redis不是“不安全”，而是不负责强一致业务。Redis适合高性能、低延迟、高并发场景；涉及余额、订单、库存最终一致性的核心数据，通常使用MySQL等数据库，Redis负责缓存、加速和削峰。
