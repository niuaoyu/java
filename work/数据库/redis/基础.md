# **持久化策略RDB AOF**

从最后一次成功生成RDB快照开始，到Redis宕机之间发生的数据修改，如果没有AOF记录，就可能丢失。

Redis 的持久化主要有两种：

1. **RDB（Redis Database）快照**： 定期拍照，把内存数据保存下来。
2. **AOF（Append Only File）追加日志**：记录每一次写操作，重启时重新读取appendonly.aof执行这些操作。

RDB：定期fork主进程，来执行写操作，主进程不影响正常工作，保存到dump.rdb文件
使用了Copy On Write（写时复制）

COW，Copy On Write（写时复制）的核心就是：**不在原地修改，而是复制后修改！**
✅ COW的真相：物理内存地址级别的复制

1️⃣ **详细的内存地址变化** 

```
【初始状态 - fork后】
物理内存地址：0x1000
数据：key="user:1" value="Alice"
    ↑                    ↑
主进程页表[0]        子进程页表[0]
(指向0x1000)        (指向0x1000)


【主进程修改 key="user:1" → "Bob"】

Step 1: 主进程尝试写入0x1000
        → 触发页错误（Page Fault）
        → 因为这页被标记为只读！

Step 2: 操作系统介入
        → 在新地址0x2000分配一页
        → 复制0x1000的内容到0x2000
        → 在0x2000上修改数据为"Bob"

Step 3: 更新主进程页表
        主进程页表[0] → 0x2000 ✅

【结果】
物理地址0x1000: "Alice" ← 子进程继续读这里
物理地址0x2000: "Bob"   ← 主进程现在读写这里

主进程页表[0] → 0x2000
子进程页表[0] → 0x1000

物理内存里有两份数据，指向不同地址！
```

2️⃣ **图解：物理内存布局** 📊

```
fork后立即：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 主进程和子进程都指向这里
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
└─────────────────────────┘

主进程修改user:1后：
┌─────────────────────────┐
│   物理内存               │
├─────────────────────────┤
│ 0x1000: user:1=Alice   │ ← 子进程仍指向这里 ✅
│ 0x1004: user:2=Tom     │
│ 0x1008: user:3=Jack    │
│ ...                     │
│ 0x2000: user:1=Bob     │ ← 主进程现在指向这里 ✅（新复制的页）
└─────────────────────────┘
```
实际COW机制：
```
✅ 正确场景：
物理地址0x1000: "Alice" → 保持不变
物理地址0x2000: "Bob"   → 新分配的页
子进程读0x1000 → 读到"Alice" → RDB快照一致 ✅
```

**问题1：dump.rdb最终保存的是这10GB内存数据吗？**

✅ **是的！** 子进程遍历的是fork瞬间的**完整快照**，即使主进程后续修改了数据，子进程读到的仍是旧值，所以dump.rdb保存的是fork时刻的10GB数据
    

**问题2：物理内存被修改，子进程也读到新数据？**

❌ **不是！** 因为：主进程修改时，**不在原物理地址修改**，而是**复制到新地址再修改**，子进程的页表仍指向旧地址，所以子进程读到的始终是旧数据
```
初始：10GB
fork后：10GB（共享）
RDB期间写入1GB数据：
  → 复制1GB到新地址
  → 总内存：10GB原始 + 1GB新副本 = 11GB
  → 不是 10GB + 10GB = 20GB ✅
```

- COW = Copy（复制到新地址） + On Write（写时才复制），这里的写时才复制是对主进程说的，复制到新地址也是对于主进程说的。
- 旧物理页保持不变，子进程继续安全读取，新物理页给主进程使用，两个进程操作**不同的物理内存地址** 🔑，这就是为什么叫"Copy-On-Write"，而不是"Modify-In-Place"！✨


RDB和AOF区别

|      | RDB      | AOF            |
| ---- | -------- | -------------- |
| 方式   | 数据快照     | 记录命令           |
| 文件   | dump.rdb | appendonly.aof |
| 恢复速度 | 快        | 慢              |
| 数据安全 | 低        | 高              |
| 文件大小 | 小        | 大              |
| 性能影响 | 小        | 稍大             |
| 适合   | 备份       | 高可靠            |


如果面试问：Redis持久化怎么实现？

> Redis提供RDB和AOF两种持久化方式。RDB通过fork子进程生成内存快照文件dump.rdb，利用Copy On Write保证主线程继续处理请求；AOF通过记录每次写命令到appendonly.aof文件，Redis重启时重新执行这些命令恢复数据。RDB恢复快但可能丢失部分数据，AOF数据安全性更高但文件更大，实际生产一般两者结合使用。

这就是 Redis 持久化的核心原理。




# 缓存穿透


什么是缓存穿透？查询一个**数据库中不存在**的数据，因为缓存也没有，所以每次请求都会"穿透"缓存，直接打到数据库上。
```
【正常查询流程✅】
用户查询 user:1000
  → Redis查询 → 命中 → 返回数据
  
或者
  → Redis查询 → 未命中 
  → MySQL查询 → 找到数据 
  → 写入Redis → 返回数据


【缓存穿透❌】
恶意用户查询 user:-1（不存在）
  → Redis查询 → 没有
  → MySQL查询 → 也没有
  → 不缓存（因为是空结果）
  → 返回null

下次再查 user:-1
  → Redis查询 → 还是没有
  → MySQL查询 → 又查一次
  → 无限循环... 💥
```
黑客就可以攻击了

```
【攻击场景】
黑客脚本：
for i in range(-1, -100000):
    requests.get(f"/api/user/{i}")

结果：
- 100万个不存在的ID
- 每个请求都打到MySQL
- MySQL瞬间被打崩 💥
- Redis完全失去保护作用
```
解决办法
1. **缓存空对象**：即使数据不存在，也在Redis中缓存一个空值，简单高效保护数据库，但会占用redis内存（大量的没用的key）
2. **参数校验** ： 在业务层拦截明显非法的请求，不正确的直接不给你查数据库的机会
3. 限流：你黑客攻击，我不让你
4. 布隆过滤器（Bloom Filter）：在Redis之前加一层布隆过滤器，快速判断数据是否可能存在。好处是 ✅ 内存占用极小（10亿数据只需约1.2GB）✅ 查询速度极快（O(k)，k为哈希函数个数）✅ 适合海量数据，坏处❌ 存在误判（可能存在的数据，实际不存在，但概率可控），❌ 删除困难（标准布隆过滤器不支持删除）

**核心思想：** 

```java
// 初始化布隆过滤器
@PostConstruct
public void initBloomFilter() {
    // 预计1000万数据，误判率0.01%
    BloomFilter<Long> bloomFilter = 
        BloomFilter.create(Funnels.longFunnel(), 10000000, 0.0001);
    
    // 将所有用户ID加入布隆过滤器
    List<Long> userIds = userMapper.selectAllIds();
    for (Long id : userIds) {
        bloomFilter.put(id);
    }
}

public User getUserById(Long id) {
    // 1. 布隆过滤器判断
    if (!bloomFilter.mightContain(id)) {
        return null; // 一定不存在，直接返回 ✅
    }
    
    // 2. 可能存在，继续查Redis
    String key = "user:" + id;
    String json = redis.get(key);
    if (json != null) {
        return JSON.parseObject(json, User.class);
    }
    
    // 3. 查数据库
    User user = userMapper.selectById(id);
    if (user != null) {
        redis.setex(key, 3600, JSON.toJSONString(user));
    }
    return user;
}
```

**Redis实现（使用Redisson）：**

```java

public void initBloomFilter() {
    RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");

    // 添加所有存在的ID
    List<Long> userIds = userMapper.selectAllIds();
    for (Long id : userIds) {
        bloomFilter.add(id);
    }
}

public User getUserById(Long id) {
```

## 实际生产方案 🏭

**推荐组合拳：**

```java
@Service
public class UserService {
    
    @Autowired
    private RedissonClient redisson;
    
    @Autowired
    private StringRedisTemplate redis;
    
    // 1. 参数校验 + 2. 布隆过滤器 + 3. 缓存空对象
    @RateLimiter(name = "getUser", permitsPerSecond = 1000)
    public User getUserById(Long id) {
        // ① 参数校验
        if (id == null || id <= 0 || id > 10000000) {
            throw new IllegalArgumentException("Invalid id");
        }
        
        // ② 布隆过滤器
        RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("user:bloom");
        if (!bloomFilter.contains(id)) {
            return null; // 一定不存在 🚫
        }
        
        // ③ 查Redis
        String key = "user:" + id;
        String json = redis.opsForValue().get(key);
        
        if (json != null) {
            return "NULL".equals(json) ? null : JSON.parseObject(json, User.class);
        }
        
        // ④ 查数据库
        User user = userMapper.selectById(id);
        
        // ⑤ 缓存结果（包括空对象）
        if (user == null) {
            redis.opsForValue().set(key, "NULL", 60, TimeUnit.SECONDS);
        } else {
            redis.opsForValue().set(key, JSON.toJSONString(user), 
                                    30, TimeUnit.MINUTES);
        }
        
        return user;
    }
}
```

## 总结 🎯

**缓存穿透 = 查询不存在的数据，导致请求穿透缓存打到数据库**

**解决方案优先级：**

1. **必选：** 参数校验 + 限流（第一道防线）
    
2. **推荐：** 布隆过滤器（海量数据场景）
    
3. **备选：** 缓存空对象（小规模场景）
    

**核心原则：** 多层防护，从外到内逐层拦截恶意请求！🛡️✨
