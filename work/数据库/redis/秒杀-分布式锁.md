# **悲观锁（Pessimistic Lock）**
**核心思想：** 我很悲观，认为**一定会发生冲突**，所以先锁住再操作，来一个锁一个，减完再释放锁，绝对不可能超卖，但别的线程就只能等待，也可能导致死锁（悲观锁认为别人一定会修改，所以先把资源锁住；如果多个线程互相持有对方需要的锁，就可能形成死循环）

**数据库实现：**
```sql
-- 加锁查询
SELECT * FROM product WHERE id = 1 FOR UPDATE;
-- 此时其他事务无法修改这行数据

-- 扣减库存
UPDATE product SET stock = stock - 1 WHERE id = 1;

-- 提交事务（释放锁）
COMMIT;
```

怎么避免死锁？
1. 统一加锁顺序（最常用）：转账
	错误：
		线程1：锁A、锁B
		线程2：锁B、锁A
	改成所有人：先锁A、再锁B（按照转账的id依次排列，id小的永远先锁），不会出现A等B，B等A
2. 设置锁超时时间
3. 检测死锁并回滚：MySQL InnoDB发现事务1等待事务2，事务2等待事务1，自动选择一个回滚


# **乐观锁（Optimistic Lock）
核心思想：** 我很乐观，认为**冲突很少**，不加锁，更新时检查是否被别人改过，✅ 性能高，无阻塞✅ 无死锁风险❌ 冲突多时，失败率高，需要不断重试

```
【流程】
线程1来了：
  ↓
查库存：10件（版本号version=5）
  ↓
计算：10-1=9
  ↓
更新时检查版本号：
UPDATE product 
SET stock = 9, version = 6 
WHERE id = 1 AND version = 5;  ← 关键！

如果version还是5 → 更新成功 ✅
如果version变了  → 更新失败，重试 ❌
```

**Redis实现：**

```
WATCH key  ← 监视这个key
GET key
计算新值
MULTI
SET key newValue
EXEC  ← 如果key被别人改了，EXEC返回nil（失败）
```

| |悲观锁|乐观锁|
|---|---|---|
|思想|一定冲突|很少冲突|
|方式|提前加锁|提交时检查|
|性能|低|高|
|死锁|可能|基本没有|
|适合|写多|读多|

一句话总结：

> 悲观锁可能导致死锁，是因为多个事务获取锁的顺序不同，互相持有对方需要的锁，形成循环等待。解决方式主要是统一加锁顺序、设置超时、死锁检测。实际开发中，高并发场景通常会优先考虑乐观锁，减少锁竞争。



# CAS失败率太高什么意思？

**CAS = Compare And Swap（比较并交换）

```
【高并发秒杀】
1000人抢10件商品

乐观锁流程：
线程1: 读库存10 → 扣减 → 更新成功 ✅
线程2: 读库存10 → 扣减 → 更新失败（版本号变了）❌ → 重试
线程3: 读库存10 → 扣减 → 更新失败 ❌ → 重试
...
线程1000: 全部失败 ❌ → 疯狂重试

【问题】
- 只有10次更新能成功
- 其他990次全部失败重试
- 失败率：99% 💥
- CPU疯狂空转，性能暴跌
```

**什么时候CAS失败率高？**

- 并发量极高（秒杀、抢券）
- 竞争同一资源（都抢同一个商品）
- 库存很少（10件商品1000人抢）
    


# 一人一单问题，为什么悲观锁可以？

```
【需求】
每个用户只能下1单

【并发问题】
用户A同时发起3个请求：
请求1: 查询订单 → 没有 → 创建订单
请求2: 查询订单 → 没有 → 创建订单
请求3: 查询订单 → 没有 → 创建订单

结果：创建了3个订单 ❌
```

### 悲观锁解决

```
synchronized (userId.intern()) {  ← 按用户ID加锁
    // 1. 查询该用户是否有订单
    Order order = orderMapper.selectByUserId(userId);
    if (order != null) {
        return "您已下过单";
    }
    
    // 2. 创建订单
    orderMapper.insert(newOrder);
}

【流程】
用户A的3个请求：
请求1：获得锁 → 查询 → 创建 → 释放锁 ✅
请求2：等待... → 获得锁 → 查询到已有订单 → 返回 ✅
请求3：等待... → 获得锁 → 查询到已有订单 → 返回 ✅
```

**为什么悲观锁可以？**
- ✅ 按用户ID加锁，只锁当前用户，不影响其他用户
- ✅ 保证同一用户的请求**串行执行**
- ✅ 查询和创建是原子操作
    


# 分布式锁怎么实现？

### 为什么需要分布式锁？

```
【单机锁的问题】
服务器1: synchronized (userId) { ... }
服务器2: synchronized (userId) { ... }

用户A的请求：
→ 请求1打到服务器1（加锁成功）
→ 请求2打到服务器2（也加锁成功）❌

JVM锁只在单机内有效！
```

### Redis分布式锁实现

#### 基础版（有问题）❌

```
加锁：
SETNX lock:userId:1001 threadId  // SET if Not eXists
→ 返回1表示加锁成功
→ 返回0表示已被锁

释放锁：
DEL lock:userId:1001
```

**问题：**

```
❌ 问题1：死锁
如果程序崩溃，锁永远不释放

❌ 问题2：误删别人的锁
线程1加锁 → 执行超时 → 锁自动过期
线程2加锁成功 → 正在执行
线程1醒来 → DEL锁（删了线程2的锁！）
```

#### 改进版 ✅

```
【加锁】
SET lock:userId:1001 threadId EX 10 NX
  ↑ key            ↑ 线程标识  ↑10秒过期 ↑不存在才设置

【释放锁】
// 先检查是不是自己的锁
if (redis.get("lock:userId:1001") == myThreadId) {
    redis.del("lock:userId:1001");
}

但这还不是原子操作！
```


# Lua脚本是什么？

**核心作用：** 让多个Redis命令**原子执行**

### 问题

```
Java代码：
String lockValue = redis.get(lockKey);
if (lockValue.equals(myThreadId)) {
    redis.del(lockKey);  ← 释放锁
}

❌ 问题：
get和del不是原子的
  ↓
线程1: get锁 → 判断是自己的
（此时锁过期，线程2加锁成功）
线程1: del锁 → 删了线程2的锁 ❌
```

### Lua脚本解决

```lua
-- unlock.lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**Java调用：**

```java
String script = 
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('del', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";

redisTemplate.execute(
    new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey),  // KEYS[1]
    threadId                              // ARGV[1]
);
```

**为什么原子？**
- Redis是单线程
- Lua脚本执行期间，Redis不会执行其他命令
- get和del在一个Lua脚本里，保证原子性 ✅

# Redisson是什么？

**Redisson = Redis的Java客户端，封装了分布式锁等功能**

### 原生Redis分布式锁的问题

```
❌ 需要自己写Lua脚本
❌ 需要处理锁续期
❌ 需要处理重试逻辑
❌ 代码复杂
```

### Redisson解决

```java
// 简单到哭 😭
RLock lock = redisson.getLock("lock:userId:1001");

try {
    // 尝试加锁，最多等10秒，锁30秒自动释放
    boolean isLocked = lock.tryLock(10, 30, TimeUnit.SECONDS);
    
    if (isLocked) {
        // 执行业务
        createOrder();
    }
} finally {
    lock.unlock();  // 自动检查是否是自己的锁
}
```

**Redisson提供的功能：**

1. ✅ **自动续期（WatchDog）**：
2. ✅ **可重入锁**：同一个线程可以**多次获得同一把锁**
3. ✅ **自动重试**：加锁失败后，不立即放弃，而是重试
4. ✅ **公平锁、读写锁**
5. ✅ **红锁（RedLock）**
    

## **可重入锁**
```java
public void methodA() {
    lock.lock();
    try {
        methodB();  ← 调用methodB
    } finally {
        lock.unlock();
    }
}

public void methodB() {
    lock.lock();  ← 又要加锁
    try {
        // 业务逻辑
    } finally {
        lock.unlock();
    }
}
```

**不可重入的问题：**

```
线程1执行methodA：
  ↓
加锁成功（锁被线程1持有）
  ↓
调用methodB
  ↓
methodB尝试加锁
  ↓
锁已被线程1持有（自己持有）
  ↓
线程1等待自己释放锁
  ↓
死锁 💀
```

**可重入锁：**

```
锁内部记录：
{
    "threadId": "thread-1",
    "count": 0  ← 重入次数
}

线程1第1次加锁：count = 1
线程1第2次加锁：count = 2（可重入！）✅
线程1第1次释放：count = 1
线程1第2次释放：count = 0（彻底释放）
```

## 锁重试
```
【不重试】
尝试加锁 → 失败 → 直接返回"系统繁忙" ❌


【重试】
尝试加锁 → 失败
  ↓
等待50ms
  ↓
再次尝试 → 失败
  ↓
等待50ms
  ↓
再次尝试 → 成功 ✅
```

## 10. 超时删除（自动续期）⏰

问题是假设，加锁时设置30秒过期，业务执行了40秒（比如网络慢），30秒时锁自动释放
  ↓
别的线程拿到锁
  ↓
第一个线程还在执行 → 并发问题 ❌
```

### Redisson的WatchDog机制 🐕

```
【加锁时】
设置锁过期时间：30秒

【后台守护线程】
每10秒检查一次（30/3 = 10）
  ↓
如果业务还在执行
  ↓
自动续期30秒 🔄
  ↓
再过10秒，再续期
  ↓
直到业务执行完，unlock释放锁
```

**代码：**

```java
// 不指定过期时间，启用看门狗
lock.lock();

// 看门狗自动续期，直到unlock
try {
    longTimeTask();  // 执行1小时也不会锁过期
} finally {
    lock.unlock();
}
```

## 11. 主从一致性问题 🏢

### 问题场景

```
【Redis主从架构】
Master(主) → Slave(从)

时间线：
1. 客户端向Master加锁 → 成功
2. Master准备同步数据到Slave
3. Master宕机 💥（数据还没同步）
4. Slave升级为新Master
5. 新Master上没有锁数据
6. 其他客户端加锁 → 成功 ❌

结果：两个客户端都持有锁！
```

### 解决方案：RedLock（红锁）🔴

**核心思想：** 向**多个独立的**Redis实例加锁

```
【5个独立的Redis实例】
Redis1  Redis2  Redis3  Redis4  Redis5

【加锁流程】
1. 向5个Redis实例发送加锁请求
2. 如果至少3个（超过半数）加锁成功 → 认为加锁成功 ✅
3. 否则加锁失败，释放所有已获得的锁

【为什么安全？】
即使Redis1主从切换，锁丢失
但Redis2、Redis3、Redis4、Redis5的锁还在
其他客户端无法获得3个锁，加锁失败 ✅
```

**Redisson使用：**

```java
RLock lock1 = redisson1.getLock("lock");
RLock lock2 = redisson2.getLock("lock");
RLock lock3 = redisson3.getLock("lock");

RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
```
