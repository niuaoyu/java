

> **ACID事务解决的是单个数据库内部的数据一致性问题。**
> **分布式事务解决的是多个服务/多个数据库之间的数据一致性问题。**
> **Redis事务（MULTI/EXEC）只是Redis提供的一组命令批量执行机制，并不等价于ACID事务，也不是完整分布式事务。**


ACID事务是什么？ACID通常指关系型数据库事务，比如MySQL。
例如：银行转账，A转账B，要么一起成功要么一起失败，失败回滚。这就是ACID。

ACID四个特性
1. Atomicity 原子性：一个事务中的操作，要么全部成功，要么全部失败。
2. Consistency 一致性：数据必须满足业务规则（转账后，不能凭空多出钱来）。
3. Isolation 隔离性：多个事务同时执行，不能互相影响。例如两个用户同时买最后一个商品，不能都买到了
4. Durability 持久性：提交commit后，数据永久保存，服务器重启数据还在。


Redis事务是什么？
1. 命令按顺序执行：但是Redis没有完整ACID，1234,12都执行完毕，3出错，也不会撤回12执行的动作。
2. 执行期间不会被其他客户端插入，类似隔离。

| |Redis事务|MySQL ACID事务|
|---|---|---|
|原子性|弱|强|
|失败回滚|❌没有|✅有|
|隔离性|基本有|有|
|一致性|需要业务保证|数据库保证|
|持久性|看RDB/AOF|redo log保证|


为什么需要分布式事务？因为现在系统不是一个数据库。例如电商用户下单，涉及订单服务、库存服务、支付服务、积分服务，每个服务有自己的数据库。如果下单成功，但是库存扣减失败，就会违反业务一致。所以需要分布式事务

目标：多个数据库、多个服务之间，也保证类似事务的一致性。





Redis在分布式事务里面干什么？

Redis一般不是承担事务核心，常见作用：
1. 分布式锁：例如抢订单，保证只有一个服务操作。
2. 状态记录：快速查询状态
3. 幂等控制：防止重复支付，第一次请求过了，第二次再请求会发现存在，直接返回。



| |ACID事务|分布式事务|
|---|---|---|
|范围|一个数据库|多个数据库/服务|
|实现|数据库自己完成|需要协调者|
|速度|快|慢|
|一致性|强一致|强一致或最终一致|
|复杂度|低|高|

MySQL事务：一个老板管理
分布式事务：多个老板，需要一个总负责人协调



**分布式事务解决方案**
1. 两阶段提交 2PC（Two Phase Commit）：协调者 Coordinator，负责指挥。参与者 Participant是各个数据库。假设下单操作，协调者问所有的数据库（订单数据库，库存数据库），准备好了吗？如果都准备好了，那就一起commit，但凡一个失败，一起rollback回滚。这就是两阶段，先问Prepare（准备阶段），再做Commit。但也有问题
	1. 同步阻塞：订单挂了，而其他数据库就一直等待
	2. 单点问题：协调者挂了，大家都不知道
	3. 性能差：锁了很多资源
2. 3PC（三阶段提交）：CanCommit、PreCommit、DoCommit，2PC是询问然后提交，3PC是询问、准备、提交，三个阶段。提前让参与者知道，事务是否可以执行，减少阻塞，但是实际互联网应用不常用。

# 七、AT模式（Automatic Transaction）

主要代表：

Seata AT模式。

思想：

自动代理数据库操作。

例如：

扣库存：

原数据：

```sql
stock=10
```

Seata记录：

undo_log：

```
以前：
stock=10
```

执行：

```
stock=9
```

如果失败：

根据undo_log：

恢复：

```
stock=10
```

类似：

数据库自动补偿。

---

AT特点：

优点：

✅ 自动化高

缺点：

❌ 依赖数据库  
❌ 性能有损

# 八、TCC模式

TCC：

三个阶段：

```
Try
Confirm
Cancel
```

---

例如扣余额。

## Try

预扣：

```
冻结100元
```

不是正式扣。

---

## Confirm

确认：

```
冻结的钱真正扣掉
```

---

## Cancel

取消：

```
释放冻结金额
```

---

流程：

```
Try

成功

Confirm


失败

Cancel
```

---

优点：

性能高。

缺点：

开发复杂。

需要自己写：

```
Try方法

Confirm方法

Cancel方法
```

# 九、SAGA模式

Saga：

长事务解决方案。

思想：

把大事务拆成多个小事务。

例如：

旅游订单：

步骤：

```
订机票

订酒店

租车
```

正常：

```
A成功
B成功
C成功
```

失败：

比如：

租车失败。

执行补偿：

```
取消酒店

取消机票
```

---

类似：

```
正向操作

A -> B -> C


补偿操作

C失败

B补偿

A补偿
```

---

特点：

最终一致。

# 十、MQ消息最终一致性

这是互联网最常用方案。

思想：

不要强行让所有服务同时成功。

通过消息重试。

例如：

订单：

```
创建订单
```

发送消息：

```
订单创建成功
```

库存服务：

收到：

```
扣库存
```

支付服务：

收到：

```
扣款
```

失败：

消息重新消费。

---

流程：

```
订单服务

创建订单

↓

MQ消息

↓

库存服务

扣库存
```

---

例如：

库存扣失败：

MQ：

```
重新发送
```

直到成功。

# 面试一句话总结：

> ACID事务解决的是单个数据库内部的一致性问题，而分布式事务解决的是多个服务、多个数据库之间的数据一致性问题。常见方案包括2PC/XA强一致方案，AT自动补偿方案，TCC业务补偿方案，Saga长事务方案，以及基于MQ的最终一致性方案。互联网系统通常追求最终一致性，而不是强一致性，因为强一致会牺牲性能和可用性。

你可以把它理解成：

```
单库：
MySQL事务(ACID)

多库：
需要事务协调机制

强一致：
2PC/XA/TCC

最终一致：
AT/Saga/MQ
```

这就是分布式事务整个体系。




面试回答：

> Redis事务通过MULTI、EXEC保证多个命令顺序执行和隔离性，但不具备传统数据库ACID事务的完整能力，没有回滚机制。分布式事务解决的是多个服务或数据库之间的数据一致性问题，常用方案包括2PC、TCC、消息最终一致性等。Redis通常作为缓存、锁、状态管理组件参与分布式事务，而不是作为核心事务数据库。
