# 《码职简历》产品需求文档 PRD V0.1

  > 产品定位：面向计算机专业求职者，根据目标岗位 JD，把用户已有经历重新整理成更符合岗位要求的简历。
  > 核心原则：不编造项目、不虚构技能、不承诺拿 Offer，只把真实经历表达得更专业、更匹配。

  ———

  ## 一、先说结论：这个产品到底卖什么？

  它不是普通的“AI 润色简历”，也不是单纯换模板。

  用户真正愿意花钱买的是：

  > 我看到一个想投的岗位，把 JD 和现有简历丢进去，几分钟后得到一份可以直接投递的针对性简历。

  所以产品核心不是“让文字更好看”，而是：

  1. 看懂这个岗位到底想要什么；
  2. 判断用户现有简历和岗位差在哪里；
  3. 从用户真实经历中找到能匹配 JD 的内容；
  4. 调整内容顺序、项目描述和技能表达；
  5. 输出一份针对该岗位的简历；
  6. 明确告诉用户哪些要求确实不具备，不能乱写。

  海外现有产品 Jobscan、Teal 等，也把“简历和 JD 的匹配分析、关键词缺口、针对岗位生成不同版本简历”作为主要功能，说明这个
  需求本身是成立的。但匹配分只能叫“JD 匹配度”，不能宣传成招聘公司的真实 ATS 分数，更不能等同于面试概率。Jobscan 自己也
  明确说明，匹配率只是帮助用户理解简历匹配程度的工具，ATS 本身并不会给简历打出这个分数。(jobscan.co
  (https://www.jobscan.co/resume-scanner?keyword=jobscan&utm_source=openai))

  ———

  # 二、产品要服务谁？

  ## 2.1 第一批核心用户

  优先服务：

  - 计算机专业大三、大四学生；
  - 计算机专业应届毕业生；
  - 工作经验在 0～3 年的初级程序员；
  - 已经写过一版简历，但不知道怎么针对 JD 修改的人；
  - 海投很多岗位，但回复率比较低的人。

  第一阶段建议重点覆盖：

  - Java 后端；
  - 前端开发；
  - 测试开发；
  - Python 后端；
  - 数据分析/数据开发；
  - C++ 开发。

  ## 2.2 暂时不重点服务的人

  第一版先不要覆盖：

  - 工作十年以上的技术管理者；
  - 产品经理、运营、销售等非技术岗位；
  - 高端算法岗、科研岗、博士岗位；
  - 海外英文简历；
  - 完全没有简历、没有项目经历的人；
  - 希望工具帮他编造实习和项目的人。

  原因很简单：用户范围越大，优化质量越难稳定，小红书上的卖点也越不清晰。

  第一阶段最好直接宣传：

  > 计算机应届生 JD 定向简历优化器

  而不是：

  > 全行业、全岗位、全能 AI 简历工具。

  ———

  # 三、用户现在有什么问题？

  计算机专业学生写简历，通常会遇到以下问题：

  ## 3.1 一份简历投所有岗位

  同一份简历同时投 Java、测试开发、数据分析，导致任何一个岗位看起来都不够匹配。

  ## 3.2 项目写成技术清单

  例如：

  > 使用 Spring Boot、MyBatis、MySQL、Redis 完成项目开发。

  这句话只说用了什么，没有说：

  - 用户负责了什么；
  - 解决了什么问题；
  - 为什么使用这些技术；
  - 做出了什么结果；
  - 和目标岗位有什么关系。

  ## 3.3 看不懂 JD 的真正要求

  JD 里经常混合了：

  - 必须具备的能力；
  - 加分项；
  - 岗位日常工作；
  - 公司为了显得专业而写的套话。

  用户不知道应该重点匹配哪些内容。

  ## 3.4 简历里有相关经历，但没有表达出来

  例如，JD 要求“接口性能优化”，用户项目中确实做过缓存和 SQL 优化，但简历只写了“负责后端接口开发”。

  不是没有能力，而是没有把能力说出来。

  ## 3.5 普通 AI 容易胡编

  用户让 AI 优化简历，AI 可能直接加入：

  - 用户没有用过的技术；
  - 用户没有做过的性能优化；
  - 编造的用户量、并发量；
  - 编造的实习成果；
  - 不符合实际的百分比数据。

  短期看起来简历变厉害了，面试一问就容易穿帮。

  ———

  # 四、产品价值主张

  产品对用户的承诺应该是：

  > 根据目标 JD，重新组织你的真实经历，让招聘方更快看到你与岗位的匹配点。

  产品不应该承诺：

  - 保证通过 ATS；
  - 保证获得面试；
  - 保证进入大厂；
  - 简历匹配度达到 90% 就一定通过；
  - 没有相关经验也可以包装出来；
  - 可以编造项目或工作经历。

  推荐宣传语：

  ### 版本一

  > 同一份简历，不要投遍所有岗位。
  > 粘贴 JD 和原简历，生成一份真正针对岗位的计算机简历。

  ### 版本二

  > 不是帮你编项目，而是把你做过的项目写得更像岗位需要的人。

  ### 版本三

  > JD 要什么、你缺什么、简历应该怎么改，一次告诉你。

  ———

  # 五、核心功能有哪些？

  ## 5.1 功能一：输入目标岗位 JD

  用户可以粘贴招聘网站上的岗位描述。

  系统需要从 JD 中提取：

  - 招聘岗位名称；
  - 工作年限要求；
  - 学历要求；
  - 必须掌握的编程语言；
  - 必须掌握的框架；
  - 数据库和中间件要求；
  - 项目经验要求；
  - 加分项；
  - 岗位主要工作；
  - 高频关键词。

  输出不要只是关键词列表，而要转换成大白话。

  例如：

  > 这个岗位最看重的是 Java 基础、Spring Boot 项目经验、MySQL、Redis和接口开发。微服务是加分项，不是最核心要求。

  ———

  ## 5.2 功能二：输入个人简历

  完整版最终可以支持：

  - 粘贴简历文字；
  - 上传 PDF；
  - 上传 Word；
  - 从历史简历中选择。

  但第一版只需要：

  > 粘贴简历文字。

  这样最稳定，也最容易快速做出来。

  ———

  ## 5.3 功能三：JD 与简历匹配分析

  系统需要告诉用户：

  ### 已经匹配的内容

  例如：

  - 有 Java 项目经验；
  - 使用过 Spring Boot；
  - 有 MySQL 数据库经验；
  - 做过 RESTful API；
  - 有 Git 协作经历。

  ### 简历中没有体现，但可能需要补充的内容

  例如：

  - JD 要求 Redis，但简历没有出现；
  - JD 要求单元测试，但简历没有提到；
  - JD 重视接口性能，但项目中没有性能相关描述；
  - JD 要求 Linux，但技能部分没有写。

  ### 明确缺失的内容

  例如：

  - 岗位要求两年工作经验，用户是应届生；
  - 岗位要求微服务实战，用户没有相关经历；
  - 岗位要求 Kafka，用户没有使用过。

  这里必须区分：

  1. 可能做过，但简历没写；
  2. 确实不会或没有做过。

  系统不能把第二种内容直接添加到简历里。

  ———

  ## 5.4 功能四：简历问题诊断

  系统需要按照严重程度给问题分类。

  ### 严重问题

  - 求职方向不明确；
  - 简历内容和 JD 基本不相关；
  - 项目只有技术名词，没有个人贡献；
  - 把课程作业包装成大型商业项目；
  - 项目描述存在明显技术逻辑错误。

  ### 一般问题

  - 句子太长；
  - 技术关键词不突出；
  - 内容顺序不合理；
  - 使用“参与、协助、了解”等弱表达；
  - 没有写清楚具体负责的模块；
  - 技能熟练度表达不可信。

  ### 可以提升的问题

  - 可以增加数字；
  - 可以解释技术选择；
  - 可以突出性能、稳定性或效率；
  - 可以把与 JD 相关的项目放到前面；
  - 可以删除无关内容。

  ———

  ## 5.5 功能五：针对 JD 优化简历

  这是用户真正付钱购买的核心结果。

  优化范围包括：

  ### 个人介绍

  根据岗位方向生成简短、可信的职业概述。

  例如：

  > 计算机科学与技术专业应届生，具备 Java 后端项目开发经验，熟悉 Spring Boot、MySQL 和 Redis，能够独立完成接口设计、数据
  > 库建模及基础性能优化。

  前提是这些内容在用户简历里能够找到依据。

  ### 专业技能

  根据 JD 调整技能顺序。

  例如，投 Java 后端时：

  1. Java；
  2. Spring Boot；
  3. MySQL；
  4. Redis；
  5. Linux；
  6. Git；
  7. 前端基础。

  而不是把 HTML、Office、Photoshop 放在前面。

  ### 项目经历

  把项目描述改成更清楚的结构：

  > 做了什么 + 怎么做的 + 解决了什么问题 + 最终结果

  例如，原文：

  > 使用 Redis 优化系统。

  优化后：

  > 针对高频商品查询接口引入 Redis 缓存，减少重复数据库访问，并设计缓存失效机制，提升接口响应稳定性。

  如果用户没有提供具体性能数字，就不能擅自写成：

  > 接口速度提升 80%。

  ### 内容排序

  把与目标岗位最相关的内容放到前面。

  例如：

  - 投 Java 岗：Java 项目放前面；
  - 投测试开发：自动化测试、接口测试内容放前面；
  - 投数据分析：Python、SQL、数据可视化项目放前面。

  ### 删除无关内容

  例如：

  - 与岗位无关的学生社团流水账；
  - 太基础的软件技能；
  - 重复的自我评价；
  - 没有信息量的“吃苦耐劳、善于沟通”。

  ———

  ## 5.6 功能六：优化前后对比

  结果页要告诉用户：

  - 原文是什么；
  - 优化后是什么；
  - 为什么这样改；
  - 这项修改对应 JD 的哪条要求。

  例如：

  | 原简历 | 优化后 | 修改原因 |
  |---|---|---|
  | 负责后端开发 | 基于 Spring Boot 完成用户及订单模块接口开发 | 明确技术栈和负责模块 |
  | 使用 MySQL | 设计用户、订单等核心数据表及索引 | 从“使用工具”改成“实际做了什么” |
  | 参与项目优化 | 针对高频查询场景增加缓存处理 | 避免“参与”这种模糊表达 |

  这个功能很重要，因为它可以建立用户信任，也特别适合在小红书做“优化前后对比”的内容。

  ———

  ## 5.7 功能七：信息真实性保护

  产品必须有一条不可突破的规则：

  > 没有出现在原简历里、没有经过用户确认的信息，不允许写进最终简历。

  例如 JD 要求 Kafka，而用户简历里没有 Kafka，系统只能提示：

  > 该岗位要求 Kafka，你的简历没有相关经历。请确认是否实际使用过。

  不能直接在技能中增加 Kafka。

  完整版可以向用户追问：

  1. 这个项目有没有使用 Redis？
  2. 接口大概有多少个？
  3. 你具体负责哪些模块？
  4. 有没有性能测试结果？
  5. 是个人项目还是团队项目？
  6. 你是否真正部署过项目？

  用户回答后，再进行二次优化。

  ———

  ## 5.8 功能八：结果导出

  理想完整版支持：

  - 在线编辑；
  - 一键复制；
  - 导出 Word；
  - 导出 PDF；
  - 导出 Markdown；
  - 保存不同岗位版本；
  - 查看历史优化记录。

  但一小时 MVP 只需要：

  > 一键复制优化后的简历文字。

  ———

  # 六、用户从打开网站到拿到简历的流程

  ## 第一步：打开首页

  首页只讲清楚三件事：

  1. 这是给计算机专业求职者使用的；
  2. 输入 JD 和原简历；
  3. 生成针对该岗位的优化简历。

  首页示例文案：

  > ### 让你的计算机简历更符合目标岗位
  >
  > 粘贴目标 JD 和原简历，查看岗位要求、简历缺口，并生成针对性优化版本。
  > 不编造经历，不乱加技能。

  按钮：

  > 免费分析一次

  首页最好提供一个“Java 后端应届生示例”，方便现场演示和没有准备材料的用户快速体验。

  ———

  ## 第二步：输入目标 JD

  页面左侧或上方放一个大文本框：

  > 请粘贴目标岗位 JD

  可以附带示例：

  - Java 后端开发工程师；
  - 前端开发工程师；
  - 测试开发工程师；
  - 数据分析师。

  ———

  ## 第三步：输入原简历

  第二个文本框：

  > 请粘贴你的原始简历

  提示用户至少包含：

  - 教育背景；
  - 专业技能；
  - 项目经历；
  - 实习经历；
  - 校园经历。

  同时提醒：

  > 可以先删除姓名、电话、邮箱、身份证号等敏感信息。

  简历包含大量个人信息，后续正式上线时需要明确说明是否保存、保存多久、由哪些模型服务商处理。若使用 OpenAI API，官方当前
  说明 API 数据默认不用于训练模型，但不同接口和配置可能存在应用状态或安全日志留存，因此不能简单宣传“绝对不保存”，而应该
  按照真实实现进行披露。(platform.openai.com
  (https://platform.openai.com/docs/models/default-usage-policies-by-endpoint?utm_source=openai))

  ———

  ## 第四步：点击“开始优化”

  按钮文案建议：

  > 分析 JD 并优化简历

  处理过程中显示进度：

  1. 正在提取岗位要求；
  2. 正在检查技能匹配度；
  3. 正在分析项目经历；
  4. 正在生成针对性简历。

  不要只放一个一直旋转的圈，否则用户容易以为页面坏了。

  ———

  ## 第五步：先看到诊断结果

  结果页第一部分显示：

  ### JD 匹配度

  例如：

  > 当前 JD 匹配度：62 分

  下面必须注明：

  > 该分数只用于比较简历内容与当前 JD 的相关程度，不代表招聘平台 ATS 分数，也不代表面试通过率。

  ### 岗位最看重的五项要求

  例如：

  1. Java 基础；
  2. Spring Boot 项目经验；
  3. MySQL；
  4. Redis；
  5. 接口设计能力。

  ### 当前简历的三个主要问题

  例如：

  6. 项目描述没有说明个人负责内容；
  7. Redis 只出现在技能栏，没有项目证据；
  8. 与岗位相关度最高的项目排在最后。

  ### 当前缺失内容

  例如：

  - Linux 使用经历没有体现；
  - 没有单元测试相关描述；
  - 没有说明项目是否完成部署。

  ———

  ## 第六步：完整版中追问必要信息

  正式产品可以追问 3～5 个问题：

  > 你是否实际使用过 Redis？

  > 你负责的是整个项目，还是其中某个模块？

  > 项目有没有真实用户量、接口数量或性能数据？

  > 项目是否部署到服务器？

  > 你是否编写过单元测试？

  用户可以选择：

  - 是，并补充；
  - 没有；
  - 不确定；
  - 跳过。

  这一步的目的是让最终简历更真实，不是增加操作负担。

  但一小时 MVP 暂时不做这一环节。

  ———

  ## 第七步：拿到优化后的简历

  输出一份完整的针对性简历，包括：

  1. 求职方向；
  2. 个人概述；
  3. 教育背景；
  4. 专业技能；
  5. 实习经历；
  6. 项目经历；
  7. 校园经历或奖项。

  页面提供：

  - 一键复制；
  - 重新生成；
  - 查看修改说明；
  - 返回修改原简历。

  ———

  ## 第八步：付费解锁

  推荐不要一打开网站就收费。

  更合适的流程是：

  ### 免费展示

  - JD 核心要求；
  - 当前匹配度；
  - 三个主要问题；
  - 优化后简历的部分预览。

  ### 付费解锁

  - 完整优化简历；
  - 每一项修改的原因；
  - 完整关键词缺口；
  - 一键复制；
  - 再生成一次；
  - 同一 JD 的二次修改。

  这样用户先看到价值，再决定付费。

  ———

  # 七、一小时能完成的现场演示 MVP

  ## 7.1 一小时 MVP 的目标

  一小时版本不是正式商用网站。

  它只需要证明一件事：

  > 输入一份计算机岗位 JD 和一份原简历，系统确实能够生成有明显差异的针对性简历。

  前提是已经有：

  - 一个可以调用的大模型；
  - 可用的模型账号或 API；
  - 一个能打开的网页环境。

  如果这些前提都没有，一小时只能完成交互原型或固定案例演示，无法保证做出稳定的真实生成产品。

  ———

  ## 7.2 一小时必须做的功能

  ### 1. 单页面

  整个网站只有一个页面，不需要多页面跳转。

  ### 2. 两个文本框

  - JD 文本框；
  - 原简历文本框。

  ### 3. 一个示例按钮

  点击：

  > 填入 Java 后端示例

  自动填入准备好的 JD 和简历，方便现场演示。

  ### 4. 一个生成按钮

  > 开始分析和优化

  ### 5. 四个结果区域

  #### 区域一：岗位核心要求

  显示 5～8 条最重要要求。

  #### 区域二：匹配度及关键词缺口

  显示：

  - JD 匹配度；
  - 已覆盖技能；
  - 缺失技能；
  - 需要确认的技能。

  #### 区域三：原简历主要问题

  显示 3～5 个问题。

  #### 区域四：优化后的完整简历

  输出可以直接复制的文字版本。

  ### 6. 一键复制

  点击即可复制结果。

  ### 7. 基础真实性提示

  结果中必须明确：

  > 未经用户确认，不会自动添加原简历中不存在的技术、项目、数字或工作经历。

  ———

  ## 7.3 一小时 MVP 不需要做得很漂亮

  只需要保证：

  - 页面能打开；
  - 输入区清楚；
  - 按钮能点击；
  - 结果分区清楚；
  - 手机浏览不至于完全错位；
  - 演示数据稳定；
  - 不出现明显胡编。

  对于小红书现场展示来说，优化前后差异是否明显，比页面动画是否高级更重要。

  ———

  ## 7.4 一小时演示版的标准流程

  现场操作控制在 1～2 分钟：

  1. 打开网站；
  2. 点击“Java 后端示例”；
  3. 页面自动填入 JD 和原简历；
  4. 点击“开始分析”；
  5. 显示岗位核心要求；
  6. 显示匹配度及三个主要问题；
  7. 显示优化后的完整简历；
  8. 点击“一键复制”。

  只要这条链路流畅，就已经能拍演示视频、发小红书笔记、测试有没有人愿意购买。

  # 八、哪些功能暂时不要做？

  ## 8.1 暂时不做用户登录

  一小时演示不需要：

  - 手机号注册；
  - 微信登录；
  - 验证码；
  - 找回密码；
  - 用户中心。

  这些功能不能证明核心需求，反而浪费时间。

  ———

  ## 8.2 暂时不做 PDF 和 Word 上传

  上传文件会带来很多问题：

  - PDF 解析失败；
  - 表格简历读取顺序错误；
  - 扫描版 PDF 无法识别；
  - Word 格式不一致；
  - 简历中的图标和双栏布局难解析。

  第一版让用户直接粘贴文字即可。

  ———

  ## 8.3 暂时不做精美模板

  先不做：

  - 十几套简历模板；
  - 颜色选择；
  - 字体选择；
  - 拖动模块；
  - 头像排版；
  - 所见即所得编辑器。

  用户最先愿意付钱的是内容优化结果，不是模板。

  模板可以后面用来提升客单价。

  ———

  ## 8.4 暂时不做账号和历史记录

  先不保存用户简历。

  用户生成后自行复制即可。

  这样可以：

  - 降低开发复杂度；
  - 降低隐私风险；
  - 不需要数据库；
  - 不需要做历史记录管理。

  ———

  ## 8.5 暂时不做在线支付

  一小时演示版不做支付。

  先验证以下问题：

  - 用户看完演示后是否愿意体验；
  - 用户是否愿意提供自己的 JD 和简历；
  - 用户认为结果有没有价值；
  - 用户是否愿意支付 9.9 元、19.9 元或更高价格。

  确定有人愿意买，再接支付。

  ———

  ## 8.6 暂时不做所有计算机岗位

  演示版只选择一个案例：

  > Java 后端应届生

  或者选择你最熟悉、素材最多的岗位。

  不要同时准备十个岗位，因为演示的关键是“一个案例优化得非常明显”。

  ———

  ## 8.7 暂时不做面试题生成

  “根据 JD 生成面试题”确实可以卖钱，但它是另一个产品环节。

  第一版只把简历优化做好。

  后续再增加：

  - 简历追问题；
  - 项目深挖题；
  - 技术面试题；
  - 自我介绍；
  - 模拟面试。

  ———

  ## 8.8 暂时不做招聘管理

  先不做：

  - 投递记录；
  - 面试日历；
  - 公司收藏；
  - Offer 对比；
  - 岗位批量抓取；
  - 浏览器插件。

  这些功能距离“简历优化”核心价值太远。

  # 十、靠什么卖钱？

  ## 10.1 用户为什么愿意付钱？

  用户不是为了“使用一次 AI”付钱。

  用户付钱是因为：

  - 不知道 JD 哪些要求最重要；
  - 不知道自己的项目怎么匹配岗位；
  - 不知道简历哪里有问题；
  - 不想每投一个岗位都手动修改；
  - 担心普通 AI 胡编；
  - 希望快速拿到能投递的版本；
  - 希望有人告诉他“为什么这样改”。

  所以收费点应该是：

  > 针对一个真实岗位，交付一份可以直接使用的定向简历。

  ———

  ## 10.2 最适合第一阶段的收费模式：按次收费

  简历优化天然适合按照 JD 次数收费。

  因为用户不会只投一个岗位，同一份基础简历需要针对不同 JD 生成多个版本。

  ### 建议测试价格

  | 产品 | 内容 | 测试价格 |
  |---|---|---:|
  | 免费体验 | JD 分析、匹配度、三个主要问题 | 0 元 |
  | 单次优化 | 一个 JD、一份完整优化简历 | 9.9～19.9 元 |
  | 求职小包 | 5 个 JD 定向优化 | 29.9～49.9 元 |
  | 求职月卡 | 30 天内多次优化，设置合理次数上限 | 59.9～99 元 |
  | AI＋人工检查 | AI 优化后由人工复核一次 | 99～199 元 |

  这些价格不是最终结论，而是第一轮需要测试的价格梯度。

  建议第一阶段从：

  > 9.9 元单次体验 + 39.9 元五次包

  开始测试。

  理由是购买门槛低，也符合用户“每个 JD 生成一个版本”的使用方式。

  ———

  ## 10.3 免费和付费怎么区分？

  ### 免费版给用户看

  - JD 最重要的五项要求；
  - 当前匹配度；
  - 已匹配的技能；
  - 三个主要问题；
  - 优化结果的前一小部分。

  ### 付费版解锁

  - 完整优化简历；
  - 完整项目经历改写；
  - 全部缺失关键词；
  - 修改前后对比；
  - 修改原因；
  - 一键复制；
  - 同一岗位重新生成一次。

  不要把免费版做得完全没用，否则用户不会相信付费结果。

  但也不要免费给出完整简历，否则用户没有付费理由。

  ———

  ## 10.4 后续可以增加的高客单价商品

  ### 商品一：项目经历深度优化

  价格可以高于普通优化，因为项目经历是计算机简历中最关键的部分。

  包括：

  - 项目真实性检查；
  - 技术逻辑检查；
  - 模块职责整理；
  - 性能数据补充建议；
  - 面试可能追问的问题。

  ### 商品二：简历＋面试包

  包括：

  - 定向简历；
  - 一分钟自我介绍；
  - 项目介绍；
  - 20 道岗位面试题；
  - 面试官可能追问的问题。

  ### 商品三：人工复核

  AI 先生成，人工进行最后检查：

  - 是否符合计算机招聘习惯；
  - 是否有技术描述错误；
  - 是否存在夸大；
  - 是否容易被面试官问穿；
  - 是否有表达不清楚的地方。

  ### 商品四：岗位方向诊断

  适合不知道投什么岗位的学生：

  - 根据技能和项目判断适合 Java、前端、测试还是数据；
  - 给出需要补充的项目和技能；
  - 生成不同方向的简历版本。

  # 十一、小红书上应该怎么卖？

  ## 11.1 不要卖“AI 工具”，要卖具体结果

  比较差的标题：

  > 我做了一个 AI 简历工具

  更合适的标题：

  > 同一份计算机简历，投 Java 岗前后差别有多大？

  > 计算机应届生简历别只写“使用 Spring Boot”

  > JD 要 Redis，但你只把 Redis 写在技能栏，真的没用

  > 我把一份 52 分的 Java 简历改成了岗位定向版

  > 为什么你的项目技术很多，面试却很少？

  内容重点应该是：

  - 原简历；
  - JD 要求；
  - 原简历的问题；
  - 修改过程；
  - 修改后的版本；
  - 用户真实反馈。

  ———

  ## 11.2 最适合小红书的内容形式

  ### 形式一：优化前后对比

  一张图展示：

  - 左边：原项目描述；
  - 右边：优化后描述；
  - 中间：为什么这样改。

  ### 形式二：岗位拆解

  例如：

  > 一份 Java 应届生 JD，到底哪五句话最重要？

  ### 形式三：反面案例

  例如：

  > 计算机简历里最没用的五句话：
  > “熟悉计算机基础”“学习能力强”“参与项目开发”……

  ### 形式四：真实体验记录

  例如：

  > 输入 JD 和简历后，工具发现了三个我自己没发现的问题。

  ### 形式五：不同岗位版本对比

  例如：

  > 同一个商城项目，投 Java 和测试开发应该怎么写？

  # 十二、产品最重要的差异化

  市场上不缺“AI 改简历”，所以不能只说：

  > 我们也能输入简历，然后自动优化。

  必须突出计算机专业垂直能力。

  ## 差异化一：懂技术岗位

  系统应该理解：

  - Spring 和 Spring Boot 不是同一个概念；
  - Redis 不是单纯“数据库”；
  - 使用过 Docker 不等于有 DevOps 经验；
  - 写过 SQL 不等于做过数据库性能优化；
  - 调用接口不等于设计过接口；
  - 做过课程项目不等于有生产环境经验；
  - “高并发”不能随便写；
  - 没有压测数据不能乱写性能提升百分比。

  ## 差异化二：不乱编

  所有新增信息必须有来源：

  - 来源于原简历；
  - 来源于用户补充；
  - 或者被标记为“建议补充”，而不是直接放进最终简历。

  ## 差异化三：一岗一版

  产品不是生成“最好的一份简历”，而是：

  > 针对每一个 JD，生成最适合这次投递的版本。

  ## 差异化四：告诉用户为什么改

  普通 AI 只给结果。

  这个产品还要告诉用户：

  - 为什么把这个项目放前面；
  - 为什么删掉某句话；
  - 为什么某个技能不能添加；
  - 这一项修改对应 JD 的哪条要求。

  ———

  # 十三、产品风险

  ## 13.1 AI 编造经历

  这是最大的风险。

  解决方式：

  - 不允许添加原简历中没有的技能；
  - 没有数字时不生成虚假数字；
  - 不确定的信息标记为“需要确认”；
  - 最终生成前提醒用户检查；
  - 后续增加事实确认步骤。

  ———

  ## 13.2 生成技术错误

  例如：

  - 把 Redis 写成关系型数据库；
  - 把 JWT 写成加密算法；
  - 把前端调用接口写成接口设计；
  - 生成不合理的系统架构；
  - 夸大项目并发和数据规模。

  解决方式：

  - 第一阶段只支持少量岗位；
  - 准备计算机简历优化规则；
  - 对技术内容进行二次检查；
  - 高客单价版本增加人工复核。

  ———

  ## 13.3 用户隐私

  简历可能包含：

  - 姓名；
  - 手机号；
  - 邮箱；
  - 学校；
  - 地址；
  - 实习公司；
  - 项目内部信息。

  解决方式：

  - 输入框提醒用户删除敏感信息；
  - 第一版不保存简历；
  - 页面明确说明数据处理方式；
  - 提供“清空全部内容”；
  - 正式上线前准备隐私政策；
  - 不要在宣传中做无法兑现的“零存储”承诺。

  ———

  ## 13.4 用户过度相信匹配分数

  解决方式：

  - 名称使用“JD 内容匹配度”；
  - 不称为“真实 ATS 分数”；
  - 不显示“面试通过概率”；
  - 不宣传“80 分以上必过”；
  - 强调分数只是辅助诊断。

  ———

  ## 13.5 用户要求编造经历

  解决方式：

  明确拒绝：

  - 虚构实习；
  - 虚构公司；
  - 虚构项目用户量；
  - 虚构性能数据；
  - 添加完全不会的技能；
  - 伪造学历、证书和奖项。

  可以帮助用户更好地表达真实经历，但不能帮助造假。

  ———

  # 十四、怎么判断 MVP 有没有价值？

  ## 14.1 一小时演示版验收标准

  只要做到以下内容，就算演示成功：

  - 用户能输入 JD；
  - 用户能输入原简历；
  - 生成时间在用户可以接受的范围内；
  - 能提取出正确的岗位重点；
  - 能发现至少三个真实问题；
  - 优化前后有明显差异；
  - 不自动添加用户没有的技能；
  - 最终结果可以复制；
  - 手机端可以完成基本操作。

  ———

  ## 14.2 第一轮商业验证目标

  第一轮不要关注注册人数，而要关注：

  1. 有多少人愿意粘贴真实 JD 和简历；
  2. 有多少人完成了一次生成；
  3. 有多少人复制了结果；
  4. 有多少人愿意支付 9.9 元；
  5. 有多少人购买第二次；
  6. 用户最愿意为什么付钱；
  7. 用户最不信任产品的地方是什么。

  建议做一个很小的验证：

  - 50 个网站访问；
  - 20 个真实生成；
  - 10 个用户反馈；
  - 至少 3～5 个真实付费订单；
  - 至少 1 个用户购买多次优化。

  如果没人愿意支付 9.9 元，先不要继续堆功能，要先检查：

  - 结果是不是和普通 AI 没区别；
  - 优化前后是不是不明显；
  - 用户是否不信任生成内容；
  - 免费部分是不是已经够用了；
  - 产品定位是不是太宽泛。

  ———

  # 十五、最终 MVP 产品定义

  ## 产品名称

  暂定：

  > 码职简历

  也可以考虑：

  - 码上简历；
  - 程序员简历助手；
  - JD 对齐简历；
  - 码职匹配；
  - 计算机简历优化器。

  ## 一句话介绍

  > 面向计算机专业求职者，根据目标 JD 分析简历差距，并生成一份不编造经历的岗位定向简历。

  ## MVP 输入

  - 一份计算机岗位 JD；
  - 一份原始简历文字。

  ## MVP 输出

  - 岗位核心要求；
  - JD 匹配度；
  - 已匹配技能；
  - 缺失或待确认技能；
  - 原简历主要问题；
  - 优化后的完整简历；
  - 一键复制。

  ## 一小时暂时不做

  - 登录；
  - 支付；
  - PDF/Word 上传；
  - PDF/Word 导出；
  - 多套模板；
  - 历史记录；
  - 在线编辑器；
  - 面试题；
  - 投递管理；
  - 多岗位批量处理；
  - 人工顾问。

  ## 初期收费方式

  > 免费诊断 + 单次付费解锁完整简历 + 多次优化包。

  ## 最核心的产品原则

  > 不编造用户没有的经历，只让真实经历更符合岗位要求。

  ## 最核心的商业卖点

  > 不是帮你生成一份万能简历，而是针对你准备投递的这个 JD，生成这一岗位专用的简历。

  ## 最适合现场演示的案例

  > 一名计算机应届生，用同一份原简历投递 Java 后端岗位。系统找出 JD 核心要求、简历缺口和表达问题，并生成一份更突出
  > Spring Boot、MySQL、Redis和接口开发经历的定向简历。
