### 泛型
定义一个类，但不指定具体要的什么数据类型，直接`<T>`
在使用的时候确定传什么类型

特点：优点是集合存储的类型统一，缺点就是集合不够灵活，单大部分需要集合还是类型统一

要理解：可以减少大量的向下转型，因为集合调用的迭代器返回的对象是object，想要专门使用子类方法，必须向下转型，使用泛型后，返回的对象就是在定义的时候的对象，比如
`List<Animal> it = new ArrayList<Animal>();Iterator<Animal> iter = it.iterator()`，
这时候使用的对象就是animal，调用animal的方法不需要向下转型，但如果调用子类方法依旧需要


### 序列化和反序列化

**序列化 = 把对象“拍扁”成字节流，用于存储或传输；反序列化 = 把字节流“复原”成对象，便于使用。**  
它的本质就是**对象状态数据的跨时空转移**——跨越时间（持久化）和空间（网络传输）

网络传输是二进制，java对象没办法网络传输，通过序列化转为二进制，反序列化转为对象，可以在不同环境下运行java对象


### 多线程

线程之间堆空间，方法区共享，但栈内存不共享

java三大变量：实例变量（存在堆空间），静态变量（存在方法区空间），局部变量（存在栈空间），栈空间天生不共享，所以不存在线程安全的问题，而堆空间和方法区空间，所有线程共享，会存在线程安全的问题

对象锁用来保护实例变量的安全
类锁用来保护静态变量的安全

**普通线程（用户线程）：会阻止 JVM 退出，JVM 必须等它跑完**  
**守护线程：不会阻止 JVM 退出，JVM 不管它有没有跑完，说杀就杀**
除此之外，并无差别，之所以用守护线程，因为有些线程的工作是辅助性的，存在的意义只是为主程序打杂，主程序都不在了，它自己存在也没意义了。比如，垃圾回收GC，日志异步，这些主程序结束存在也没意义。但有些比如，文件下载，数据库写入，订单相关，必须是普通进程，不能被中断。
守护线程被强制杀死时，**不会执行 finally 代码块，也不会做任何资源释放的收尾工作**，是直接"截断"的。所以：⚠️ 凡是涉及到**文件写入、数据库事务、网络传输**这类需要"有始有终"的操作，**绝对不要**用守护线程去做，否则数据可能损坏或丢失。



#### start() vs run()

start()**真正创建一个新的线程**，让 CPU 去调度它，新线程和当前线程（比如 main）**并发执行**，谁先跑完不确定。
run()**只是普通的方法调用**，跟你调用任何一个普通方法没有任何区别。它不会创建新线程，而是在**当前线程**里老老实实、同步地把 run() 里的代码执行完，执行完了才能往下走。

```java
public class StartVsRun {
    public static void main(String[] args) {
        Thread t = new Thread(() -> {
            System.out.println("子线程: " + Thread.currentThread().getName());
        });
        
        System.out.println("调用前: " + Thread.currentThread().getName());
        
        t.start();   // 或者换成 t.run() 对比着跑一下
        
        System.out.println("调用后: " + Thread.currentThread().getName());
    }
}
```

**用 `t.start()`：** （顺序甚至可能是"调用后"先打印出来，因为两个线程谁先谁后不确定）

```
调用前: main
子线程: Thread-0     ← 新开了一个线程在跑，名字不是main
调用后: main
```

**如果换成 `t.run()`：**

```
调用前: main
子线程: main          ← 注意！还是 main 线程，没有新线程
调用后: main
```

三行严格按顺序打印，因为本质上就是**在 main 线程里顺序调用了一个方法**，跟写 `t.run();` 和写别的方法调用（比如 `doSomething();`）完全一样。

`start()` 才是"启动线程"这个动作本身；`run()` 只是"线程要执行的任务内容"，你不通过 `start()` 去触发它，它就只是一个躺在那里的普通方法，谁调用它就在谁的线程里跑。


⚠️谁调用了线程的方法，这就是当前线程，但是所有的java方法不都在mian线程里被调用？但实际上并不都是main线程，这怎么理解？

不是"所有方法都在 main 线程里被调用"，而是：

- **写在 main 方法体里的代码**（比如 `t1.start()` 这一行）确实是 main 线程在执行
- 但 `start()` 一旦被调用，**它的职责就是去创建一个新的线程实体**，然后是**这个新线程自己**去执行 `run()` 里的代码——这一步已经跳出 main 线程的范围了，是并发发生的

所以 `run()` 里 `currentThread()` 获取到的是谁，取决于"物理上是哪个线程在跑这段代码"，而不是"这段代码写在源码的哪个文件/哪个类里"。t1、t2、t3 各自 start 后，各自的 run() 是各自的新线程在跑，所以各自拿到的 currentThread 自然是它们自己。



#### 共享对象

共享对象：**多个线程都能访问到的同一个对象（同一块内存），而不是各自新建的、各玩各的对象**

最经典的例子——**多个窗口卖同一批火车票**

反例：先看一个"不共享"的错误写法
```java
class SellTicket extends Thread {
    private int ticket = 100;  // 每个线程对象自己的票数
    
    public void run() {
        while (ticket > 0) {
            System.out.println(Thread.currentThread().getName() + "卖出第" + ticket + "张票");
            ticket--;
        }
    }
}

public class Test {
    public static void main(String[] args) {
        SellTicket t1 = new SellTicket();  // new 了一个对象
        SellTicket t2 = new SellTicket();  // 又 new 了一个对象
        SellTicket t3 = new SellTicket();  // 又 new 了一个对象
        
        t1.start();
        t2.start();
        t3.start();
    }
}
```
这里 `t1`、`t2`、`t3` 是**三个完全独立的对象**，各自持有一份 `ticket = 100`。结果就是：一共卖出了 `100 + 100 + 100 = 300` 张票！——这就是没有共享数据导致的问题（多个人各自拿着自己的 100 张库存去卖，互不知道对方）

这种情况下加 `synchronized` **完全没用**，因为 t1、t2、t3 压根不存在"抢同一个资源"的竞争关系，你锁 `this` 也只是锁住了它自己那一份，没有意义。


**正确写法：造一个"共享对象"**
```java
class SellTicket implements Runnable {
    private int ticket = 100;  // 注意：这份数据只有一份
    
    public void run() {
        while (ticket > 0) {
            synchronized (this) {   // this 就是共享对象！
                if (ticket > 0) {
                    System.out.println(Thread.currentThread().getName() + "卖出第" + ticket + "张票");
                    ticket--;
                }
            }
        }
    }
}

public class Test {
    public static void main(String[] args) {
        SellTicket task = new SellTicket();  // ← 关键：只 new 了一个对象！
        
        Thread t1 = new Thread(task, "窗口1");
        Thread t2 = new Thread(task, "窗口2");
        Thread t3 = new Thread(task, "窗口3");
        // t1、t2、t3 三个线程，都是围着同一个 task 对象转的
        
        t1.start();
        t2.start();
        t3.start();
    }
}
```

关键区别在哪

||反例|正确写法|
|---|---|---|
|`new` 了几次 `SellTicket`|3次（t1、t2、t3 各自 new）|**1次**（task 只 new 一次）|
|`ticket` 这份数据|3份，各自独立|**1份**，大家抢的是同一份|
|`synchronized(this)` 里的 `this`|指向3个不同对象，锁不住彼此|**指向同一个 task 对象**，t1/t2/t3 抢的是同一把锁|

在正确写法里，`task` 这一个对象，被同时传给了 `t1`、`t2`、`t3` 三个线程去执行——**这个 `task` 就是"共享对象"**。三个线程操作的 `ticket` 变量，物理上就是同一块内存里的同一个数字，所以才有"抢票"这个真实的竞争关系存在，`synchronized(this)` 锁的也正是这同一个 `task`，才能真正把它们排队起来。

- `synchronized("abc")` 之所以危险地"能用"，是因为字符串常量 `"abc"` 在**字符串常量池**里天生只有一份，所有线程写 `"abc"` 拿到的都是同一个对象——这恰好符合"共享对象"的要求（但正因为太容易共享，反而可能不小心把不相关的线程也绑在一起，所以不推荐这么写）。
- `synchronized(obj2)` 如果 `obj2` 是在构造方法里 `new` 出来的局部变量，那**每个线程传进来的 `obj2` 都是不同的对象**——根本不共享，锁了个寂寞，起不到任何排队效果。

`synchronized(xxx)` 括号里锁的这个 `xxx`，**必须是所有相关线程手里拿到的、指向内存中同一块地址的那个对象**，而不是每个线程各自 `new` 出来的、看起来一样但实际上是不同对象的东西。


#### **锁一个方法和锁一个变量，差别是什么？**

灵活与否，如果只需要某个资源，不需要锁方法体的其他内容，就直接锁这个变量synchronized（this）

情况一：锁 `this`（共享对象就是当前对象本身）
**场景**：银行账户取钱，多个人（线程）操作**同一个账户对象**。
```java
class Account {
    private double balance = 10000;
    
    public void withdraw(double money) {
        synchronized (this) {   // this 就是这个 Account 对象
            double before = balance;
            double after = before - money;
            balance = after;
        }
    }
}

public class Test {
    public static void main(String[] args) {
        Account acc = new Account();   // 只 new 了一个账户对象
        
        Thread t1 = new Thread(() -> acc.withdraw(1000));
        Thread t2 = new Thread(() -> acc.withdraw(2000));
        // t1、t2 操作的是同一个 acc，所以 synchronized(this) 里的 this
        // 对 t1、t2 来说，指向的是同一个对象，能锁住
        
        t1.start();
        t2.start();
    }
}
```
**判断依据**：只要所有线程用的是**同一个 Account 对象**，`this` 就有效。

情况二：锁一个方法（同步方法，锁死是 this，没得选）
跟情况一其实是同一回事，只是写法更"暴力"——直接把整个方法锁死：

```java
class Account {
    private double balance = 10000;
    
    public synchronized void withdraw(double money) {   // 整个方法体都被锁住，锁的就是this
        double before = balance;
        double after = before - money;
        balance = after;
    }
}
```

跟情况一效果一样（因为锁的都是 `this`），差别只在于：这里锁的是**整个方法**，情况一里你可以只锁方法里的一部分代码。

情况三：锁 `obj2`（一个额外指定的、跟 this 无关的对象）
**场景**：比如你有两种资源要保护——"取钱"和"记录日志"是两件互不相关的事，你想用**不同的锁**分别控制，让它们可以并发执行，互不干扰。这时候就不能都用 `this`（否则会互相卡住），而是专门造一个对象当"专属锁"。
```java
class Account {
    private double balance = 10000;
    private final Object lockMoney = new Object();   // 专门给"取钱"用的锁
    private final Object lockLog = new Object();      // 专门给"记日志"用的锁

    public void withdraw(double money) {
        synchronized (lockMoney) {   // 用 lockMoney 这个对象当锁，跟 this 无关
            double before = balance;
            balance = before - money;
        }
    }
    
    public void writeLog(String msg) {
        synchronized (lockLog) {    // 用另一把独立的锁
            // 写日志的逻辑
            System.out.println(msg);
        }
    }
}
```
**这里的关键**：`lockMoney` 是用 `final` 修饰的**成员变量**（属于 Account 对象），不是方法里的局部变量，也不是每次调用都 `new` 一份——只要多个线程操作的是**同一个 Account 对象**，那这个 `Account` 对象里的 `lockMoney` 就只有一份，天然就是共享对象，可以拿来当锁用。

这么做的好处是：`withdraw()` 和 `writeLog()` 用的是**两把不同的锁**，两个线程一个在取钱、一个在写日志，**不会互相排队等待**，因为它们抢的锁根本不是同一把——这就是"锁范围更精细"带来的效率提升。

|情况|锁的是什么|典型用途|
|---|---|---|
|`synchronized(this)`|当前对象自己|最常见，简单场景，锁整个对象的状态|
|`synchronized 方法`|固定锁 this，锁整个方法体|图省事，方法体里全都要保护时用|
|`synchronized(obj2)`（自定义锁对象）|一个专门 new 出来、跟 this 无关的**成员变量**对象|需要**多把锁分开控制**、缩小锁的粒度、避免不相关操作互相卡住时用|

**核心判断标准永远是同一条**：不管锁的是 `this` 还是 `obj2`，只要这个"锁对象"对所有相关线程来说，指向的是**内存中同一个对象**（而不是各自 new 出来的不同副本），它就能起到排队的作用。
