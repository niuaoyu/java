   - 第1轮：问第1~2层（定位+架构）
   - 第2轮：问第3~4层（流程+实现）
   - 第3轮：问第5层（吸收迁移）

**3、每次讲代码必须遵守“5层解释法”**

```text
第 1 层：业务问题
第 2 层：系统解决方案
第 3 层：模块职责
```

**4：让我自己实现“Mini Version”**

这是必须有的一步，不能停留在“我看懂了”，在理解核心链路以后，把项目缩小成：**一个最小可运行版本**

例如原项目10 万行代码，20 个模块，不要照抄，而是抽象成500 行，3～5 个核心模块，要求：
1. 保留原项目最核心的思想，删除所有非核心功能（一些ui等非业务代码）
2. 不追求生产级
3. 不追求代码漂亮
4. 先让我跑起来

然后拆成有核心模块的，最简单版本

每一步必须说明：**这一小步是在复现原项目的哪一个设计思想？** ==感觉项目读到这一步，设计思想已经知道了，就不需要再说明了，除非一开始项目太大，读不下去，先拆小demo再读的==



**5：从“复现”到“迁移”**

Mini Version 完成以后，不要继续照抄 GitHub，开始问**这个设计思想还能解决什么问题？**

请帮我提炼成：

```text
原项目场景
 ↓
遇到的问题
 ↓
采用的设计
 ↓
设计解决的问题
 ↓
抽象成通用能力
 ↓
其他业务场景
```

例如不要告诉我：“这个项目用了 Agent。”。而是让我理解：“当任务无法由固定流程解决，需要根据中间结果动态决定下一步动作时，可以采用这种控制机制。”

看看这个思想能否迁移。最终形成我的“工程能力”

最后不要再总结“这个项目用了 XXX 技术。”

而是输出：
1. 我从这个项目学到了哪些工程能力？
	能力 1：如何拆分复杂系统
	能力 2：如何设计模块边界
	能力 3：如何设计 Agent Workflow
	能力 4：如何处理状态
	能力 5：如何设计 Tool
	能力 6：如何处理失败
	能力 7：如何让系统可扩展
2. 每个能力来自项目中的什么代码？
3. 哪些东西值得我以后写项目时复用？
4. 哪些东西只是这个项目的特殊实现，不值得照搬？
5. 如果我以后自己从 0 做一个项目，应该如何应用？

最终形成：**我的项目设计方法论**


**6、每一个阶段都要有“完成标准”**

不要告诉我 “理解了就进入下一阶段。”，必须给我具体验收标准。

例如阶段 2 完成标准，你给出

```text
用户输入从哪里进入？
第一步调用什么？
第二步调用什么？
核心状态在哪里？

```

# 阶段 3：从“运行过程”理解代码

现在开始真正读代码。但不要按照文件顺序。按照 **运行时执行顺序**

阅读。

每读一个核心函数，必须按照下面格式解释：

① 这个函数解决什么问题？先用人话。
② 它在整个系统中的位置？告诉我：上游是谁、当前函数、下游是谁
③ 输入是什么？
④ 输出是什么？
⑤ 核心逻辑是什么？用伪代码先解释：拿到输入、判断 X、调用 Y、处理 Z、返回结果
⑥ 再解释真实代码，这时候才进入代码。
⑦ 为什么这样写？这是重点。不要只告诉我 “这里用了策略模式。”，而要告诉我： “作者遇到了什么问题，所以才需要策略模式。”
⑧ 如果不用这个设计会怎样？让我理解：**设计模式不是知识点，而是问题逼出来的。**

==这里其实太细了，一个函数里的东西大致能知道在做什么==


# 阶段 4：理解核心架构

等我理解主链路以后，再开始总结架构。

不要先贴一个漂亮的架构图骗我理解。

而是从已经读懂的代码反推出架构。

分析：

### 1. 分层

例如：

```text
Interface Layer
Application Layer
Domain Layer
Infrastructure Layer
```

或者项目真实存在的分层。

### 2. 模块边界

告诉我：

> 为什么 A 模块没有直接调用 C，而要经过 B？

### 3. 依赖关系

分析：

```text
谁依赖谁
谁不能依赖谁
为什么
```

### 4. 数据流

分析：

```text
数据从哪里来
经过哪些处理
最后到哪里
```

### 5. 控制流

分析：

```text
谁决定下一步做什么？
```

特别关注：

- Agent
    
- Router
    
- Workflow
    
- Event
    
- Callback
    
- Tool
    
- Queue
    
- Scheduler
    
- State
    
- Context
    

这些控制系统行为的东西。

# 七、建立“代码阅读优先级”

对项目中的代码进行分类：

### S级：必须吃透

核心业务链路、核心抽象、核心算法、核心 Agent/Workflow、关键状态管理。

### A级：必须理解作用

重要基础设施、接口、配置、数据访问、模型调用。

### B级：知道作用即可

工具类、辅助代码、通用封装。

### C级：暂时跳过

部署、脚本、测试辅助、非核心功能等。

告诉我：

> **哪些代码必须读，哪些代码可以暂时不读。**

# 十、最重要的输出方式

不要把目标定义成：“让我看懂代码。”，而要定义成： **让我最终具备“看到一个陌生系统，可以自己拆、自己追、自己理解、自己复现、自己设计”的能力。**

所以每一次讲解都必须回答：
What：这是什么？
Why：为什么需要它？
How：它到底怎么实现？
Transfer：我以后自己写项目时，什么时候应该想到它？
