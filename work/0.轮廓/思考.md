

如何设计一个系统，让即使你不想努力的时候，也能继续前进。

计划要具体，足够具体才能做下去，现在的任务就是如何具体步骤，同时不是要一口气吃个胖子，要有修改的方法，螺旋上升。

先别攻击自己，做不到都赖系统没设计好，继续微调即可。


真正厉害的人，很多时候也不想干。区别是什么？普通人：我不想干 → 那我今天不干。优秀的人：我不想干 → 但是现在是训练时间 → 开始。

不靠鸡血，激情，”我要成功“，”不能对不起父母，要让父母过上好日子“，这种激素不稳定，现在的问题就是把“行动”建立在“感觉”上。感觉好学习（也不尽全力），感觉不好就逃避。高手把行动建立在：**身份 + 系统 + 规则。** 
1. 身份，回答我是什么样的人？不是口号，不是说”我要努力，我该学习，成为开发高手“，这些都不是现在时，都是未来，未来的身份和现在的行动没有绑定，所以不会驱动今天做事情，要是自己设定的今天的默认行为，”我是每天训练开发能力和写论文的人，我是一个每天会产出commit的人，我是到点就写，改，测代码的人“，下雨了，普通人会想要不要跑？但运动员会觉得，我是运动员所以我要训练，这符合身份。怎么获得？不靠喊，**必须每次承诺的任务完成**，先行动做到，再逐渐修改大脑回路，从根上相信，一点点建立自信心（健身就是如此，做的多了，就相信自己是一个自律的人了），建立自己对自己的身份认同，相信自己说过的话一定可以做到，同时完不成也要有正当原因（==不可能完不成的，要怎么设计才是关键？**最低做到的=上一次真的100%能够做到的量，而不是自己觉得应该做的量** ，设计的考虑是，要对我写代码，看论文重要的事情，同时也要考虑当下状态不好，可能要打球，可能要出差，可能很多正当理由的情况下，也能做到的事情==）
2. 系统：这就是具体的动作，不需要热血，口号，励志视频，也能做的事情。不需要每天决定今天说什么，而是系统提前设计好，去掉自己每天做决策的过程，只有行动就行了，过程结果不好当天微调就行了，一个完整的闭环。**现在之所以痛苦，就是输入多，但是产出和反馈不多，不清晰**。
3. 规则，最关键，解决最要命的问题，**每次都临场做决策 → 决策消耗 + 模糊 → 逃避**。最关键的就是减少自己和自己的战斗，规则是”如果发生X，就必须做Y“，今天有点累不想训练，那就最起码去热身拉伸一会，这是最起码能做到的，这是规则不是商量，累——拉伸，失败也没关系，连续两天都没做到就需要修改方法

3. 有微调的方法，方向，可以让我能螺旋上升。每次耍手机，焦虑的断线时刻，一般是这些原因造成的
	- **任务太模糊** → 解决办法是，再拆小，拆到 20~40 分钟可完成
	- **任务太难没有抓手、三天都没完成当天的量，或三天都轻松完成** → 解决：说明问题还是太大或者太小，对应的就是减量或加量，在这个过程记录实际用时vs计划用时，这就是微调的依据，是太简单还是太难，不用猜。
	- **没有反馈** → 解决：加“测试/可视化指标/每周面试”
	- **环境被劫持（手机）** → 解决：物理隔离/软件限制/休息不碰信息流
	- **能量不足（困/累）** → 解决：把最低动作做完即可，不做补偿性爆肝
4. 反馈也要具体，不能说学java，而是要把结果具体出来，今天写了三个算法，并记录思考过程、不要说提升开发能力，而是要写了一个注册接口


身份重要，因为认同后，无压力就能做到，那自我认同的身份靠什么？靠行动获得，行动怎么设计？这就靠系统设计清楚，需要目标清楚，需要拆足够细，当遇到常见的失败需要固定的规则处理

健身能做下去是因为时间定，地点定，动作定，强度渐进，反馈定，没有给自己思考的余地，都是固定的，不需要太深的思考，很自然的努力

A类 - 项目工程任务（核心，占比最高）：项目的每个功能模块拆出来的具体任务
B类 - 算法练习任务：面试必考，每天固定小剂量
C类 - 计算机基础补充：面试会问的redis/mysql/网络/操作系统概念，缺什么补什么
D类 - Agent专项任务：如果走agent方向，RAG/prompt/框架使用相关
E类 - 简历/面试任务：模拟面试、简历迭代，阶段性穿插

	1. 每天的最小完成怎么定？（==因为是工程训练，最低完成也要是工程证据，否则只会用看了半小时来糊弄自己==）暂定代码地板流，每天一个八股commit。论文地板流，每天对重建任务的理解（方法，输入输出，对比，指标，数据，任何都行），不要觉得少，现在需要的是每天commit不断线。等14天之后再加量

	1. 渐进超负荷：加复杂度，加边界数量，多做结果接口和场景，加质量健壮要求（测试，异常，并发，日志，重构），加部署和可观测，前期ai搭架子多，逐步减少ai依赖，熟练后不断提升速度。（这些暂时不考虑，暂时先固定好动作，搭建好mvp，其他的ai都可以给思路怎么优化）

> **"走偏、卡死、重写"不是练习失败的副产物，它就是练习本身。** 你要提高的"强度"，不是每天多敲多少行，而是每天多撞几次墙、多复盘几次为什么撞。

你问"加 Service 是为什么、加 Redis 是因为什么"——这个问题在书里和 AI 嘴里的答案你都看过，但没进脑子。原因很简单：**你没有先经历过"没有 Service"和"没有 Redis"时的疼**。所有架构决策的"为什么"，都是对某种疼的回应。没疼过，就不可能真懂。

**“先让 AI 跑通 MVP，我针对 doc 学习”——这个方法的上限就是 L2**。 整个过程中是读者，不是作者。看懂一万行代码也练不出从空目录搭建的能力，就像读一百本小说成不了小说家。你的四个瓶颈（独立实现弱、选型无依据、拆分无标准、无闭环经验）全是“作者肌肉”缺失的症状。所以核心改动：**把 AI 从“施工队”降级为“教练”**，**把“读项目”升级为“重建项目”**。 你现有的 MVP + doc + 验收标准框架全部保留，只换角色分配。

# 学习的方法
1. 多给自己些耐心，一遍不会别苛责自己，一个知识点一次没看会，再看一遍，再看一遍，再看一遍，再看一遍，看了十遍再说，二十遍再说，直到理解深刻到脑子里有下意识了，有突触建立了就算是可以了。
2. 如何学项目？不要担心，所有的后端或者程序都有一个模板，各种层，不需要担心，熟练就行。
	1. 刚看视频操作的时候，看完一个，先别开始下一个，把流程图对着脑子画下来，这就是自己的收获，一点点做。
	2. 等到所有的模块都这样做完后，代码也跑通了，事实上每一个模块都知道数据是怎么跑的，包括如何配置
	3. 开始对某个部分（常见的功能）进行复制，比如，新加一个属性或者表，从头到尾改一遍数据，算第一次微调项目
	4. 接着让ai使劲拷打自己更改的这个部分，问出各种面试题以及答案。
3. 如何记笔记？只记三点，第一是框架图（需要做完项目后理解透，自己画一个），第二是每个模块，每个步骤只记“为什么？”，为什么用这个不用别的？这个要多问ai，最后是只记环境搭建或者其他的bug问题。
	1. 记笔记，但凡答案确定（不变的），不理解就用ai，留下一些思考点即可，永远不要复制粘贴，直到一个知识点经常忘，那可以记下来，否则永远不**要当知识点的搬运工，只当思考点的搬运工**。
4. 如何看读代码？永远不要一句句的读，永远是先看整体后再读细节。
